# 15. S6 v2 — 어제의 "6.1배"는 재현되지 않았다

실행: 2026-09-16, EC2 m6id.4xlarge · **72 run** (skew 2 × codec 3 × cap 4 × 3회) · 78분
원자료: `results/s6v2/`

---

## 결론 먼저

> **어제 `docs/13`에 쓴 "디스크를 조이면 6.1배 느려진다"는 중앙값 효과가 아니었다.
> 같은 조건에서 어떤 run은 막히고 어떤 run은 안 막히는 양봉(bimodal) 현상이고,
> v1은 n=2라 느린 쪽이, v2는 n=3이라 빠른 쪽이 중앙값이 됐을 뿐이다.**
>
> 그리고 오늘 아침에 세운 대체 규칙(`총 쓰기량 / 대역폭`)도 **성립하지 않는다.**
> 예측 대비 실측 비율이 0.43 ~ 5.11 로 흩어진다.

**S6의 메커니즘은 미해명으로 되돌린다.** 어제·오늘 `docs/13`에 쓴 두 규칙 모두 철회한다.

---

## 1. 양봉 증거

v2, skew 64, cap 50 MB/s, n=3:

| codec | median | min | max |
|---|---:|---:|---:|
| lz4 | 23.5s | 23.3s | **159.2s** |
| none | 16.9s | 16.9s | **137.8s** |
| zstd | 23.0s | 22.7s | 23.6s |

lz4·none은 3회 중 1회만 폭발한다. zstd는 3회 모두 안정.

대조적으로 **cap 100에서는 매우 안정적이다**:

| cap | lz4 median | min | max |
|---:|---:|---:|---:|
| 100 | 85.3s | 85.1s | 85.5s |
| 200 | 41.0s | 37.0s | 46.1s |

즉 **cap 50에서만 양봉**이다. 중간 cap에서는 깨끗하게 단조 증가한다.

## 2. v1 vs v2 (skew 64, task 시간 median)

| cap | | lz4 | zstd | none |
|---:|---|---:|---:|---:|
| 0 | v1 | 26.9 | 27.0 | 20.9 |
| | v2 | 22.7 | 23.4 | 17.7 |
| 50 | **v1** | **164.4** | 27.2 | **158.0** |
| | **v2** | **23.5** | 23.0 | **16.9** |
| 100 | v2 | 85.3 | 22.5 | 17.0 |
| 200 | v2 | 41.0 | 22.9 | 17.2 |

v1의 cap 50 값(164.4 / 158.0)은 v2의 **max**(159.2 / 137.8)와 거의 같다.
같은 현상을 봤는데 표본이 적어 중앙값이 그쪽으로 떨어진 것이다.

## 3. 오늘 아침 규칙도 안 맞는다

`wall_time ≈ 총 쓰기량 / 대역폭` 예측 대비 실측 비율:

| skew | codec | cap | 총쓰기(MiB) | 예상(s) | 실측 wall(s) | **비율** |
|---:|---|---:|---:|---:|---:|---:|
| 16 | zstd | 200 | 1,506 | 8 | 38 | **5.11** |
| 16 | none | 100 | 8,981 | 90 | 42 | **0.46** |
| 64 | lz4 | 50 | 7,980 | 160 | 96 | **0.60** |
| 64 | none | 50 | 9,191 | 184 | 218 | **1.19** |

0.43 ~ 5.11 로 흩어진다. **규칙이 아니다.**

> 게다가 분모로 쓴 `pgpgout` 자체가 신뢰할 수 없다 — run 전체(배수 포함) 구간에서
> 재기 때문에 cap 조건에 따라 같은 워크로드인데도 2,799 ~ 8,021 MiB 로 변한다.
> **측정이 순환적이다.** Spark 자체 회계(`total_written_bytes`, 이번에 파서에 추가)를
> 써야 한다: skew 64 기준 lz4 9,508 / none 11,012 / zstd 5,154 MiB.

## 4. 그런데 여기서 write-volume 가설이 깨진다

`total_written_bytes` 로 보면 **`none`이 가장 많이 쓴다** (11,012 MiB, lz4의 1.16배).
그런데 cap 100·200 에서 `none`은 **전혀 안 느려진다** (17.0 / 17.2s, 무제한 17.7s와 동일).
반면 lz4는 9,508 MiB로 더 적게 쓰는데 **85.3 / 41.0s로 크게 느려진다.**

**쓰는 양이 많은 쪽이 오히려 멀쩡하다.** 총 쓰기량으로는 설명이 안 된다.

## 5. 그래도 단단한 것

| | |
|---|---|
| **codec 간 차이는 일관됨** | zstd·none은 cap 전 구간에서 평탄, lz4만 cap에 민감 |
| **cap 100·200 에서 lz4의 단조 증가** | 22.7 → 41.0 → 85.3s, n=3에서 산포 0.4s 미만 |
| **skew 16은 전 조건에서 무영향** | 4.3~5.3s, cap과 무관 |
| **wall은 늘고 task는 안 늘 수 있다** | 버퍼드 I/O가 비용을 뒤로 미룬다 — 이건 v1·v2 모두에서 성립 |

## 6. 무엇을 잘못했나

1. **n=1~2로 결론을 냈다.** v1에서 "조건 간 차이가 6배인데 산포는 1% 미만"이라고 썼는데,
   그 산포는 **같은 mode 안에서만** 1%였다. mode가 둘인 걸 못 봤다.
2. **양봉을 median으로 뭉갰다.** min/max를 같이 보지 않았다.
   `plot_s6.py`가 IQR 오차막대를 그렸지만 n=1~2에서는 IQR이 의미가 없다.
3. **순환적인 지표(pgpgout)를 분모로 썼다.** cap이 걸리면 측정 구간 자체가 늘어난다.

## 7. 다음에 할 것

1. **cap 50에서 반복을 크게 늘린다** (n=10+). 양봉의 비율과 조건을 잡아야 한다.
2. **어느 mode인지 사전에 예측 가능한가?** 느린 run의 `samples.csv`를 빠른 run과 비교.
   v1 타임시리즈에서 본 "두 덩어리 스톨"이 느린 mode에만 있는지 확인.
3. **lz4만 민감한 이유.** 총 쓰기량으로 설명 안 됨. 쓰기 *패턴*(블록 크기, 빈도)의 차이일 수 있다.
4. 분모는 `total_written_bytes`(Spark 회계)를 쓴다. `pgpgout`은 보조 지표로만.
