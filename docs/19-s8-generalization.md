# 19. S8 — 핵심 결론은 `sort` 밖에서도 성립하는가?

실행: 2026-09-19 · EC2 m6id.4xlarge (spot) · **99 run, 오류 0건** · 약 30분
스크립트: `runner/s8_sweep.sh` · 그림: `results/s8/figures/generalization.png`

---

## 0. 요약

| 검증 대상 | 판정 |
|---|---|
| **A. 계단은 실행 풀 포화가 만든다** (S1/P1) | ✅ join 에서 재현. **단, 천장은 연산자마다 다르다** |
| **B. 첫 spill = 0.757 × pool / N** (S3) | ✅ **1/N 은 그대로. 계수는 연산자마다 다르다** (sort 0.757 / join 0.643) |
| **C. 비용은 레코드로 지불된다** (S2/P2) | ⚠️ sort 는 방향 확인, join 은 **반복 산포에 묻힘** |
| **음성 대조군 (`count`)** | ✅ 통과. 전 구간 평평 |
| **`agg`** | ❌ **판정 불가** — 지표가 안 잡히고 이 규모에선 풀에 닿지도 않는다 |

한 줄로 줄이면: **법칙은 일반화되고 상수는 일반화되지 않는다.**

## 1. 왜 했나

S1·S2·S3 의 결론이 **전부 `sort` 워크로드에서 나왔다.** join 은 S4(AQE)에서만
썼고 집계는 한 번도 안 돌렸다. 블로그 초안의 한계 항목에도 그렇게 적혀 있었다.

그런데 우리가 주장하는 메커니즘 — `UnsafeExternalSorter` 가 실행 풀을 채우다
넘친다 — 은 **sort 전용이 아니어야 한다.** shuffle 뒤 한 파티션을 메모리에
쌓는 연산이면 구조가 같다. 확인하지 않으면 "sort 에서만 봤다"로 남는다.

## 2. 설계

| 파트 | 축 | run |
|---|---|---:|
| A. cliff | sort · join · agg · **count** × skew 8·16·24·32 × 3 rep | 48 |
| B. 1/N | sort · join · agg × cores 1·2·4·6 @ skew 16 × 2 rep | 24 |
| C. 레코드 | sort · join · agg × record-skew 1·8·32 × 3 rep | 27 |

풀 720 MiB 고정 · partitions 200 · AQE off · cores 4 (B 제외).

**`count` 를 넣은 것이 설계의 핵심이다.** partial aggregation 이 skew 를 map
단계에서 흡수해야 하는 **음성 대조군**이다. "어떤 워크로드든 skew 면 느려진다"는
동어반복이고, **흡수되는 쪽이 실제로 흡수돼야** 메커니즘 주장이 선다.
여기서까지 계단이 보였다면 우리 해석이 틀린 것이었다.

## 3. A — 계단은 join 에서 재현된다. 천장은 다르다

cores=4, 3 rep 평균.

| | skew 8 | 16 | 24 | 32 | |
|---|---:|---:|---:|---:|---|
| **wall (s)** | | | | | |
| sort | 30.8 | 32.5 | 36.3 | 38.1 | ×1.24 |
| join | 25.9 | 26.3 | 28.8 | 29.6 | ×1.15 |
| agg | 22.2 | 22.1 | 22.3 | 22.3 | ×1.01 |
| count | 5.5 | 5.4 | 5.4 | 5.4 | ×0.99 |
| **peak exec mem (MiB)** | | | | | |
| sort | 197 | 558 | **712** | **712** | |
| join | 245 | 592 | **616** | **616** | |
| count | 8 | 8 | 8 | 8 | |
| **spill (MiB)** | | | | | |
| sort | 139 | 138 | 687 | 689 | |
| join | 119 | 116 | 579 | 892 | |
| count | 0 | 0 | 0 | 0 | |

hot 파티션이 읽은 바이트(`sr_bytes_max`)는 sort 와 join 이 **완전히 동일**하다
(291.5 / 564.5 / 818.0 / 1053.9 MiB). 입력은 같다.

### 재현된 것

- **cliff 위치가 같다.** 둘 다 skew 16 → 24 사이에서 spill 이 평탄구간을 벗어난다.
  S3 에서 cores=4 의 cliff 가 skew 24 였던 것과 일치한다.
- **`count` 는 완전히 평평하다.** 5.5 → 5.4초, peak 8.2 MiB, spill 0.
  hot 파티션이 애초에 안 생긴다 (`sr_bytes_max` 0.1 MiB). 음성 대조군 통과.

### 재현되지 **않은** 것 — 천장

sort 는 **712.0 MiB**, join 은 **616.1 MiB** 에서 멈춘다. 포화 구간(skew 24·32)
6 run 씩 전부 **소수점까지 같은 값**이다. 노이즈가 아니다.

그럴듯한 설명: SortMergeJoin 은 한 태스크 안에서 **양쪽을 각각 정렬한다.**
메모리 소비자가 둘이라 하나가 풀 전체를 못 가져간다.
**확인하지 않았다.** 확인하려면 태스크 내 consumer 별 할당을 계측해야 한다.

> 천장이 연산자마다 다르다는 건 실무에서 의미가 있다. "실행 풀이 720 MiB 니까
> 712 까지 쓴다"는 sort 기준의 숫자고, join 은 그보다 **100 MiB 일찍** 넘친다.

### `agg` 는 답할 수 없다

`peak_exec_mem_max` 가 agg 의 모든 run 에서 **min = max = 0** 이다.
이건 "메모리를 안 썼다"가 아니라 **이 지표로는 안 보인다**는 뜻이다.
`peakExecutionMemory` accumulator 는 `UnsafeExternalSorter` 계열이 채우고,
`ObjectHashAggregate` 는 보고하지 않는다. (`count` 는 8,650,736 바이트를
모든 run 에서 똑같이 보고한다 — HashAggregate 의 고정 맵.)

게다가 agg 는 이 규모에서 풀에 닿지도 않는다. `collect_list(substring(payload,1,8))`
라서 map-side partial aggregation 이 shuffle 을 20배 줄인다
(hot 파티션 52 MiB vs sort 의 1054 MiB).

**두 이유가 겹쳐서 agg 로는 A·B 를 판정할 수 없다.** 결과가 아니라 한계다.

## 4. B — 1/N 은 sorter 의 성질이다. 계수는 아니다

skew 16 평탄구간, 첫 spill 을 raw 바이트로.

| | 1c | 2c | 4c | 6c |
|---|---:|---:|---:|---:|
| sort | 570,674,401 | 285,769,478 | ~146,732,413 | ~91,415,053 |
| join | 485,255,643 | 242,637,388 | 121,329,016 | (cliff 넘음) |

**첫 spill × N (MiB)**

| | 1c | 2c | 4c | 6c | 퍼짐 |
|---|---:|---:|---:|---:|---:|
| sort | 544.2 | 545.1 | 559.7 | 523.1 | 7.0% |
| join | **462.8** | **462.8** | **462.8** | — | **0.0%** |

**계수 = 첫 spill ÷ (pool/N)**

| | 1c | 2c | 4c |
|---|---:|---:|---:|
| sort | 0.756 | 0.757 | 0.777 |
| join | 0.643 | 0.643 | 0.643 |

join 은 1c·2c·4c 에서 **462.8 MiB 로 완전히 같다.** 6c 는 이미 cliff 를
넘어서 (579 MiB) 평탄구간이 아니므로 제외했다.

> **1/N 스케일링은 일반화된다. 계수 0.757 은 sort 고유다.**
> S3 에서 "0.757 이 어디서 오는지 모른다"고 적었는데, 이제 하나 더 안다 —
> **연산자마다 다르다.** 여전히 왜 그 값인지는 모른다. join 이 0.643 인 것도
> 천장이 616/720 = 0.856 인 것과 딱 맞아떨어지지 않는다.

sort 의 퍼짐 7.0% 는 S3(skew 8 에서 0.4%)보다 크다. skew 16 이 평탄구간의
끝자락이라 그렇다. 실제로 sort 4c 5 run 중 1 run 만 150,302,727 로 튀었다.

## 5. C — 레코드 지배는 방향만 확인된다

record-skew 모드는 **설계상 바이트를 균일하게 유지한다** (hot=64B 좁은 행,
cold=2048B 넓은 행). 그래서 hot 파티션이 전체의 약 1/200, 즉 **55~65 MiB** 밖에
안 된다. 풀(720 MiB) 근처에 가지도 못한다.

| | R=1 | R=8 | R=32 | |
|---|---:|---:|---:|---|
| hot records | 29,921 | 164,904 | 663,779 | ×22.2 |
| hot bytes (MiB) | 55.3 | 55.2 | 64.8 | ×1.17 |
| sort wall (s) | 18.86 | 18.89 | **19.57** | +0.70s |
| join wall (s) | 19.72 | 19.76 | 19.93 | +0.21s |

반복 산포와 비교하면:

```
sort  Δwall +0.70s  vs  최대 반복 산포 0.25s   -> 산포보다 큼. 의미 있다
join  Δwall +0.21s  vs  최대 반복 산포 0.61s   -> 산포에 묻힌다
```

바이트가 완전히 고정은 아니라서(+17%) 그 몫을 빼보면, S2 의 4.95 ns/byte 로
Δbytes 9.5 MiB 는 **+0.049초**밖에 설명하지 못한다. sort 의 +0.70초 중 **7%**다.
나머지는 레코드가 맞다.

**다만 S2 의 1741 ns/record 는 여기서 과대예측한다.** 633,858 레코드 × 1741ns =
1.10초를 예측하는데 실측은 0.70초다 (실측 계수 1,106 ns/record).

이건 새로운 문제가 아니다. **S4 가 이미 같은 것을 발견했고** (`docs/12` §111:
"1741 ns/record는 0.7M 레코드에 대해 1.16초를 예측하는데 실제는 282ms였다"),
그래서 파티션을 4배 키워 S4b 를 다시 돌렸다. S8 의 C 파트는 그 한계를
**독립적으로 재현한 것**이다.

> 1741 ns/record 는 **spill 이 일어나는 큰 파티션 영역에서 적합된 국소 계수**다.
> 작은 파티션에 외삽하면 안 된다. S2 문서의 "국소 선형화" 경고가 맞았다.

## 6. 판정

| | |
|---|---|
| 계단 메커니즘 | ✅ **sort → join 일반화.** 위치는 같고 천장은 연산자가 정한다 |
| 1/N 법칙 | ✅ **일반화.** 계수는 연산자마다 다르다 (sort 0.757 / join 0.643) |
| 레코드 지배 | ⚠️ **sort 에서 방향·자릿수 확인.** join 은 이 규모에서 측정 불가 |
| 음성 대조군 | ✅ `count` 가 전 구간 평평 — 메커니즘 해석이 반증되지 않았다 |
| `agg` | ❌ 판정 불가 (지표 미보고 + 풀에 안 닿음) |
| 신뢰도 | 높음 — 99/99 성공, 포화 천장이 6 run 씩 소수점까지 동일 |

## 7. 남은 구멍

1. **`agg` 를 제대로 재려면** `peakExecutionMemory` 말고 executor 메모리
   타임시리즈나 `ObjectHashAggregate` 계측이 필요하다. 그리고 partial
   aggregation 을 우회하는 집계(예: `percentile_approx` 없이 정렬 기반)를 써야
   풀에 닿는다.
2. **join 천장 616 MiB 의 원인은 추론이다.** 두 sorter 가 풀을 나눠 쓴다는 읽기가
   가장 정합적이지만 직접 보지 않았다.
3. **C 파트는 규모가 작다.** 큰 파티션에서의 레코드 지배는 S4b(P=50)가 이미
   다뤘다. 여기서 다시 키우는 건 중복이라 하지 않았다.
4. **여전히 단일 노드다.** 여러 노드에 걸친 네트워크 shuffle 은 이 프로젝트 전체가
   한 번도 건드리지 않았다.
