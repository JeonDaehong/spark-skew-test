# 10. S1 — Cliff 탐색: 방법론과 결과

실행: 2026-09-13 · 35 run · 생성 ~25분 + 실행 38분
원자료: `results/s1/summary.csv` · 그림: `results/s1/figures/`

---

## 결론 먼저

> **skewed partition은 커지기만 하는 게 아니라 바이트당 비용이 비싸진다.
> 다만 그 비용은 계속 올라가지 않고, 두 개의 평탄 구간 사이에서 한 번 계단식으로 뛴다.**
>
> - skew 8–16: **10.2 ms/MB** (평탄)
> - skew 32–64: **13.6 ms/MB** (평탄) — **+31%**
> - 전이 지점은 **실행 메모리 풀이 천장(720MB)에 닿는 바로 그 지점**과 일치한다.

산포(IQR 0.56 / 0.82)에 비해 계단의 크기(3.2 ms/MB)가 **약 40배**다. 노이즈가 아니다.

**명제 P1("skew 대비 latency는 선형이 아니고 특정 지점에서 기울기가 급변한다") → 참.**
단, 예상했던 "가속하는 붕괴"가 아니라 **두 평탄 구간 사이의 계단**이다. 이 차이가 중요하다 (아래 §7).

## 1. 무엇을 물었나

```
동일한 총 바이트에서 skew 만 키울 때, latency 는 어디서 꺾이는가?
그리고 그 지점은 노이즈보다 큰가?
```

이 질문에 답이 안 나오면 8주 계획 전체가 무의미하다. 그래서 S1을 가장 먼저 돌렸다.

### skew를 만드는 방법

전체 N rows 중 비율 `f`를 **단일 hot key**에 몰아준다. 나머지는 10,000개 cold key에 균등. 파티션 P일 때 hot key는 정확히 한 파티션에 떨어지므로:

```
S = ((1-f)N/P + fN) / ((1-f)N/P) = 1 + f·P/(1-f)
⇒ f = (S-1) / (P + S - 1)
```

skew 64 → f = 0.2395 (전체의 24%가 한 key).

**검증됨** — 목표 대비 실측 skew:

| 목표 | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---|---|---|---|---|---|---|
| 실측 | 1.4 | 1.9 | 3.9 | 7.8 | 15.7 | 31.4 | **63.0** |

바이트 통제 오차 **-3.1~-3.3%** (parquet 푸터/메타데이터 오버헤드). 전 skew에서 동일하므로 비교에 영향 없음.

> payload는 sha2 기반 고엔트로피, parquet은 `uncompressed`. 압축이 걸리면 "총 바이트 고정"이라는 통제가 깨진다.

## 3. 왜 이 워크로드인가

```python
spark.read.parquet(8GiB)
  .repartition(200, "key")        # shuffle — hot key가 한 파티션에 몰림
  .sortWithinPartitions("key", "payload")
  .write.format("noop")           # 결과는 안 쓰고 연산만 강제
```

**`groupBy().count()`를 쓰면 안 된다.** map-side partial aggregation이 hot key를 mapper당 1행으로 접어버려서 **skew 효과 자체가 사라진다.** (`--workload count`로 대조군 실행 가능 — S1에서는 미실행)

정렬은 접을 수 없다. hot 파티션의 **모든** 레코드가 `UnsafeExternalSorter`를 통과해야 한다. 그게 우리가 보려는 경로다:

```
LongArray 성장 (16 bytes/record)
  → execution memory 고갈
  → spill
  → spill write 가 page cache 로
  → dirty page 누적 → writeback
```

`noop` sink는 Spark 벤치마크 표준 싱크로, 디스크 쓰기 없이 전체 연산을 강제한다.

## 4. 사이징 역산 — cliff이 sweep 한가운데 오게 만들기

cliff을 찾으려면 cliff이 측정 범위 안에 있어야 한다. 그래서 역산했다.

```
실행 메모리 풀 = (exec_mem - 300MB) × spark.memory.fraction(0.6)
MEM=1500m      → (1500-300) × 0.6 = 720 MB

median 파티션  = 8 GiB / 200 = 41 MB
hot 파티션     ≈ 41 MB × S
in-memory 배율 ≈ 1.3 (스모크 실측: shuffle read 235MB → peak exec 310MB)

spill 시작 S ≈ 720 / (41 × 1.3) ≈ 13
```

→ sweep(1~64) 한가운데. **실측 결과 전이는 skew 16→32 사이에서 일어났다.** 예측 13과 부합.

> ### 사이징 전에 알아야 했던 것 (스모크에서 발견)
> "task는 execution memory의 1/N만 쓴다"는 **틀렸다.** 1g 풀(434MB)에서 peak execution memory가 **310MB**까지 올라가고도 spill이 안 났다. 1/2N~1/N은 *보장 하한*이고, 다른 task가 놀면 한 task가 **풀 전체**를 가져간다.
> 이걸 모르고 1/N으로 사이징했으면 cliff이 범위 밖으로 나갔을 것이다. 그리고 이 사실 자체가 **RQ2(cores-per-executor가 skew 내성을 정한다)의 출발점**이다.

## 5. 측정 체계

### Spark 이벤트로그에서 (`parse/parse_eventlog.py`)

`SparkListenerTaskEnd` 이벤트를 전부 파싱 → task 하나 = CSV 한 줄. 그중 **shuffle read가 있고 task 수가 가장 많은 스테이지**를 reduce 스테이지로 자동 식별해 집계한다 (skew 효과는 거기에만 나타난다).

| 뽑는 것 | 왜 |
|---|---|
| task duration p50/p90/max | **cliff 곡선의 y축.** p50은 통제 확인용(아래 §6) |
| `sr_bytes_max` / `sr_records_max` | hot 파티션의 실제 크기 — 정규화의 분모 |
| `peak_exec_mem_max` | **실행 풀 천장에 닿았는지** — 전이 메커니즘의 핵심 |
| `spill_mem` / `spill_disk` | 천장에 닿은 결과 |
| `gc_ms` | JVM 레이어 기여분 |
| `remote_to_disk` | 200MB 초과 블록 fetch-to-disk (RQ7) — **Spark UI가 spill로 안 세는 I/O** |

### `/proc` 에서 (`runner/sampler.py`, 0.25초 간격)

Spark 메트릭만으로는 절대 안 보이는 것들. 같은 run에서 같이 찍어야 나중에 겹쳐볼 수 있다.

| 뽑는 것 | 왜 |
|---|---|
| `/proc/meminfo` Dirty·Writeback | spill이 page cache에 흡수되는 중인지, 밀리는 중인지 |
| `/proc/pressure/io` full | **태스크가 실제로 I/O 때문에 멈춰 있었는지** (PSI) |
| `/proc/pressure/memory` | 메모리 압력 stall |
| `/proc/vmstat` `pgpgout` | 실제 writeback 양 |
| `/proc/stat` ctxt, procs_blocked | 스케줄링 경합, D-state |

run 전후 스냅샷의 **차이(delta)**를 기록하므로, 그 run이 유발한 양만 분리된다.

## 6. 재현성 통제

| 장치 | 내용 |
|---|---|
| **run마다 `drop_caches`** | `sync` 후 `/proc/sys/vm/drop_caches`에 3. 앞 run의 page cache가 다음 run을 오염시키는 것 방지 |
| **rep을 바깥 루프에** | skew별로 몰아 돌리면 시간 순서 효과(디스크 상태, 발열, 백그라운드)가 skew와 교락된다. rep마다 전체 skew를 한 바퀴 돈다 |
| **median + IQR** | 평균 금지. 5회 반복 전부를 그림에 점으로 찍는다 — 산포를 숨기지 않는다 |
| **판정 기준** | 구간 median 변화량 > 그 구간 IQR. 이걸 만족 못 하면 "꺾였다"고 말하지 않는다 |
| CPU governor | WSL2는 cpufreq가 없어 고정 불가·불필요 |

**p50이 통제 확인 지표다.** 총 바이트가 고정이면 hot 파티션이 커질수록 나머지는 작아져야 한다. 실측 p50: 288 → 309 → 283 → 291 → 274 → 260 → **216 ms** — 평탄하거나 약간 감소. **통제가 지켜졌다는 증거.**

### 원시 곡선은 오해를 부른다

`cliff.png`의 max 곡선은 2278 → 24352 ms로 10배 넘게 뛴다. 하지만 그건 당연하다 — hot 파티션이 54MB에서 1798MB로 33배 커졌으니까. **"데이터가 많아서 오래 걸린다"는 발견이 아니다.**

배증당 증가 배수(2.0이면 정확히 선형):

| 구간 | 1→2 | 2→4 | 4→8 | 8→16 | 16→32 | 32→64 |
|---|---|---|---|---|---|---|
| 배수 | 0.40 | 2.14 | 1.46 | 2.00 | **2.45** | 1.75 |

16→32만 초선형이고 32→64는 오히려 아선형이다. 이것만 보면 "일시적 혹"으로 보인다. 하지만 hot 파티션 크기 자체가 `f=(S-1)/(P+S-1)`로 포화하기 때문에(skew 64에서 f=0.24) 상단에서 아선형으로 보이는 것이다.

### 정규화가 진짜 답이다

**hot 파티션 1MB를 처리하는 데 걸리는 시간**으로 나누면:

| skew | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---:|---:|---:|---:|---:|---:|---:|---:|
| **ms / MB** | 42.11 | 12.89 | 13.64 | **10.05** | **10.36** | **13.58** | **13.55** |
| IQR | 7.27 | 18.97 | 1.63 | 0.26 | 0.56 | 0.82 | 0.54 |
| peak MB | 72 | 96 | 176 | 184 | 544 | **712** | **712** |

- skew 1–2는 **노이즈 구간**. hot 파티션이 아직 지배적이지 않아 max task가 데이터가 아니라 straggler다. IQR(18.97)이 값(12.89)보다 크다. 해석하면 안 된다.
- **skew 8–16: 10.05 → 10.36 ms/MB — 평탄.** 변화 0.31, IQR 0.26~0.56. 구분 불가 = 같은 값.
- **skew 32–64: 13.58 → 13.55 ms/MB — 평탄.** 역시 같은 값.
- **두 평탄 구간 사이에 +31%의 계단.** 변화량 3.22 vs IQR 0.56/0.82 → **노이즈의 약 40배.**

### 전이 지점의 메커니즘

계단이 일어난 skew 16→32 구간에서 동시에 벌어진 일:

| | skew 16 | skew 32 |
|---|---|---|
| hot 파티션 | 547 MB | 1022 MB |
| **peak execution memory** | 544 MB | **712 MB ← 천장(720MB)에 닿음** |
| spill to disk | 137 MB | **687 MB** (5배) |
| ms/MB | 10.36 | **13.58** |

skew 16까지는 hot 파티션이 실행 풀 안에 들어간다(544 < 720). skew 32부터는 안 들어간다. **peak가 712MB에서 고정(pin)되고**, 초과분이 전부 spill로 나간다. 바이트당 비용은 그 순간 한 번 뛰고, **그 뒤로는 다시 평탄하다.**

> 즉 이건 "무너지기 시작하는 지점"이 아니라 **"두 개의 서로 다른 실행 체제(regime) 사이의 경계"**다.
> regime A = 인메모리 정렬, regime B = 외부 정렬. 각 체제 안에서는 비용이 바이트에 선형이다.

## 8. 예상과 달랐던 것 3가지

### (a) RQ4 신호가 없다 — 커널은 개입하지 않았다

PSI `io.full`: 2.0 / 1.9 / 1.9 / 2.1 / 2.1 / 2.2 / **2.6 s** — 사실상 평탄.
page cache Dirty 최고치: **1335~1370 MB로 전 skew 동일.**

skew가 64배 변하고 spill이 0 → 1238MB로 변하는 동안 **커널 I/O 스톨은 거의 그대로다.** Dirty 값도 skew가 아니라 8GiB parquet 스캔이 만든 것이다.

→ **`docs/04-novelty-risk.md`의 리스크 2가 현실화됐다.** 이 규모에서는 writeback 스로틀링이 발동조차 안 한다. spill 1.2GB는 16GB 박스의 `dirty_background_ratio`(1.6GB)를 못 넘긴다.
→ **P5를 검증하려면 spill 총량을 훨씬 키우거나 `vm.dirty_ratio`를 강제로 낮춰야 한다.** S5/S6 설계를 이에 맞춰 수정해야 한다.

### (b) RQ7은 이 설정에서 측정 불가

`remote_to_disk_total = 0`, 전 skew.
mapper 200개가 hot 파티션을 나눠 쓰므로 **블록 하나당 1798MB/200 ≈ 9MB.** `maxRemoteBlockSizeFetchToMem`(200MB) 근처에도 못 간다.
→ RQ7을 보려면 **mapper 수를 크게 줄여야** 한다 (예: 입력 파티션 8~16개). S4 설계에 반영할 것.

### (c) 정체불명의 고정 spill 136.5MB

skew 4 / 8 / 16에서 `spill_disk_total`이 **정확히 136.54MB로 동일**하다. hot 파티션은 142 → 283 → 547MB로 4배 커지는데 spill은 그대로다.

→ skew와 무관한 **고정 배경 spill**이 존재한다. hot task가 아닌 다른 무언가가 매번 같은 양을 흘리고 있다.
→ **미해결. S2에서 task 단위로 내려가 확인할 것** (`results/s1/*/tasks.csv`에 task별 원자료가 있다).
→ 이것 때문에 "spill > 0"을 cliff 마커로 쓰면 **잘못된 지점(skew 4)을 가리킨다.** 마커를 "실행 풀 포화(peak ≥ 천장의 95%)"로 교체했다.

## 9. 한계 — 이 결과로 주장하면 안 되는 것

1. **단일 환경.** WSL2 / local 모드 / 12 vCPU / 16GB / NVMe. 클러스터 결과가 아니다.
2. **local 모드**라 executor 간 네트워크 shuffle이 없다. shuffle read가 전부 로컬이다.
3. **8 GiB · 200 파티션 · 1500m**이라는 한 점. 계단의 **위치**는 이 설정에 종속이다.
   (계단의 *존재*와 *메커니즘*이 결과이고, 숫자 32는 결과가 아니다.)
4. **디스크·하드웨어 레이어 주장 불가.** `dd oflag=direct`가 6.0 GB/s로 나오는 환경이다 (`01-local-feasibility.md`).
5. **워크로드 1종(sort).** join·aggregation으로 일반화되는지는 S8에서 확인.
6. **+31%라는 수치는 이 조건의 값**이다. 다른 메모리/코어 설정에서 같은 폭일 이유가 없다 — 그걸 보는 게 S2/S3다.

| B6 (재현성) | ✅ 신호 구간 IQR이 값의 5~6% |
| RQ4 (커널) | ⚠️ **이 규모에서 신호 없음** — S5/S6 재설계 필요 |
| RQ7 (fetch-to-disk) | ⚠️ 이 설정에서 측정 불가 — mapper 수 축소 필요 |

### 계획 조정

**8주 계획은 유지한다.** 다만 3가지를 수정한다.

1. **S2(row width)로 그대로 진행.** 계단의 *위치*가 bytes로 정해지는지 records로 정해지는지가 다음 질문이다. 지금 결과는 "실행 풀(bytes)이 천장"이라고 말하지만, LongArray는 record당 16바이트라서 **row 폭을 줄이면 같은 바이트에서 record가 늘어 계단이 더 일찍 와야 한다.** 이게 P2의 핵심 예측이고, 지금 설계로 바로 검증 가능하다.
2. **S5/S6(커널) 재설계.** 현 규모로는 writeback이 발동하지 않는다. spill 총량을 키우고(executor 메모리 축소) `vm.dirty_ratio`를 5%까지 낮춰 **강제 발동시킨 뒤** 정상값에서 재현되는지 보는 순서로 바꾼다. 그래도 안 나오면 **"이 규모에서는 커널이 개입하지 않는다"가 결론**이고, 그것도 정당한 결과다 (깊이의 원칙).
3. **S4에 mapper 수 축소 조건 추가** (RQ7용).

### 블로그 가치

지금 결과만으로도 쓸 게 있다.

- ❌ "skew가 심하면 느려진다" — 누구나 안다
- ✅ **"바이트당 비용은 두 구간에서 각각 일정하고, 그 사이에 한 번 계단이 있다. 계단의 위치는 실행 메모리 풀 천장이 정한다."**
- ✅ **"task는 execution memory의 1/N만 쓴다는 통념은 틀렸다"** — 풀 전체를 가져간다. 이것이 계단 위치를 정한다.
- ✅ **"spill 메트릭을 cliff 지표로 쓰면 안 된다"** — 136.5MB 고정 배경 spill이 skew 4부터 잡혀서 엉뚱한 곳을 가리킨다. 올바른 지표는 peak execution memory의 포화다.

세 번째는 실무자가 바로 써먹을 수 있는 진단 조언이다.
