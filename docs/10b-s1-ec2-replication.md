# 10b. S1 EC2 재현 — 계단은 머신의 성질인가, Spark의 성질인가

실행: 2026-09-13, EC2 m6id.4xlarge · 35 run · 24분
원자료: `results/s1_ec2/summary.csv` · 그림: `results/s1_ec2/figures/`
대조: `docs/10-s1-methodology-and-results.md` (로컬 WSL2 파일럿)

---

## 왜 다시 돌렸나

S1 로컬 결과는 **한 점**이었다. Ryzen 5600X + WSL2 + 가상 디스크. 이대로 블로그에 쓰면 "네 노트북 얘기 아니냐"는 반론을 피할 수 없다.

그리고 로컬 환경에는 두 가지 구조적 한계가 있었다 (`docs/01-local-feasibility.md`):
- `dd oflag=direct`가 6.0 GB/s — 호스트가 쓰기를 흡수해 블록 레이어 측정이 불가능
- 다른 작업(게임 등)의 CPU·RAM·디스크 경합

**동일 설정을 완전히 다른 하드웨어에서 재현**하면, 계단이 머신 특성인지 Spark의 성질인지 갈린다.

## 환경 대조

| | 로컬 (파일럿) | EC2 |
|---|---|---|
| CPU | AMD Ryzen 5 5600X 6C/12T | **Intel Xeon 8375C (Ice Lake) 16 vCPU** |
| RAM | 32GB (WSL2에 16GB) | **61GB** |
| 디스크 | ext4.vhdx on NVMe (가상) | **인스턴스스토어 NVMe 885GB (직결)** |
| OS | WSL2 커널 6.18 | Ubuntu 24.04 네이티브 |
| `dd oflag=direct` | 6,000 MB/s ← 가짜 | **675 MB/s** ← 실측 |
| `rotational` | 1 (오보고) | **0** |
| Spark / JDK | 4.0.1 / 21 | 4.0.1 / 21 (동일) |

**Spark 설정은 전부 동일**: 8 GiB · 200 파티션 · 4 core · 1500m · AQE off · lz4 · sort 워크로드 · 5회 반복.

## 결과

### 바이트당 비용 — 계단이 같은 자리에 있다

| skew | 8 | 16 | **32** | 64 |
|---|---:|---:|---:|---:|
| 로컬 ms/MB | 10.05 | 10.36 | **13.58** | 13.55 |
| EC2 ms/MB | 9.17 | 8.90 | **10.92** | 11.29 |
| 계단 크기 | | | **로컬 +31% · EC2 +22.7%** | |

절대값은 다르다 (CPU도 디스크도 다르니 당연). **꺾이는 위치는 동일하다 — skew 16 → 32 구간.**

### peak execution memory — MB 단위까지 동일

| skew | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 로컬 (MiB) | 72 | 96 | 176 | 184 | 544 | **712** | **712** |
| EC2 (MiB) | 72 | 96 | 176 | 184 | 544 | **712** | **712** |

**이것이 이 재현의 핵심 결과다.** 하드웨어가 완전히 달라도 값이 같다. 즉 이 천장은 머신이 아니라 **Spark의 unified memory manager가 결정한다**. 실행 풀 상한 `(1500-300)×0.6 = 720 MiB`의 99%에서 고정된다.

### spill — 배경 spill까지 재현

| skew | 1 | 2 | 4 | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 로컬 (MiB) | 0 | 0 | 136.5 | 136.5 | 136.5 | 687.1 | 1237.7 |
| EC2 (MiB) | 0 | 0 | 136.5 | 143.3 | 136.5 | 687.2 | 1237.7 |

S1에서 수수께끼였던 **136.5 MiB 고정 배경 spill이 그대로 재현**됐다. 로컬 아티팩트가 아니라 결정론적인 Spark 동작이다. **여전히 미해결** — `results/*/*/tasks.csv`로 task 단위 추적이 필요하다.

### EC2가 훨씬 정밀한 측정기다

| | 로컬 IQR | EC2 IQR |
|---|---:|---:|
| ms/MB @ skew 16 | 0.56 | **0.03** |
| ms/MB @ skew 1 | 7.27 | **0.33** |
| task_ms_max @ skew 1 | 393 | **18** |

로컬에서 "노이즈 지배라 해석 불가"로 버렸던 skew 1~2 구간이 EC2에서는 깨끗하게 측정된다. 산포가 **10~20배** 작다. 전용 머신 + 경합 없음의 효과다.

이후 스테이지에서 **반복을 5회 → 3회로 줄인 근거**가 이것이다.

### 커널 신호는 여기서도 조용하다

PSI `io.full`: 4.6 / 4.6 / 4.8 / 5.2 / 4.6 / 4.9 / **5.6 s** — skew가 64배 변하고 spill이 0 → 1.24 GiB로 변하는 동안 사실상 평탄.
page cache Dirty 최고치: 5,900~6,010 MiB로 전 skew 동일 (61GB RAM의 `dirty_background_ratio` 10% = 6.1GB 부근).

실제 NVMe로 바꿨는데도 **RQ4의 신호는 나오지 않았다.** spill 1.24 GiB로는 61GB 박스의 writeback 스로틀링을 건드리지 못한다.
→ S5/S6에서 **cgroup으로 RAM을 제한하거나 `vm.dirty_ratio`를 강제로 낮춰야** 한다.

## 도중에 잡은 결함: `drop_caches`가 조용히 실패하고 있었다

첫 EC2 실행에서 매 run마다 경고가 떴다:

```
[run] WARN: drop_caches 실패 (Permission denied: '/proc/sys/vm/drop_caches')
```

로컬 WSL은 root로 돌았지만 EC2는 `ubuntu` 사용자다. 61GB RAM이면 데이터셋 7개(56GB)가 통째로 page cache에 남아, **로컬과 프로토콜이 달라져 비교 자체가 성립하지 않는다.**

15분 버리고 두 가지를 고쳤다 (`runner/run_one.py`):
1. `sudo -n` 폴백 추가
2. **실패하면 즉시 중단**하는 가드 추가 — 명시적으로 끄려면 `--no-drop-caches`를 줘야 한다

> **교훈**: 통제 장치는 실패할 때 **시끄러워야** 한다. 조용히 꺼진 채 도는 것이 가장 위험하다.
> 경고를 stderr로만 흘리지 말고 실행을 멈춰야 한다.

## 판정

| 항목 | 결과 |
|---|---|
| 계단의 존재 | ✅ 재현 |
| 계단의 위치 (skew 16→32) | ✅ 동일 |
| 계단의 메커니즘 (실행 풀 포화) | ✅ 동일, **peak 값이 MB 단위까지 일치** |
| 배경 spill 136.5 MiB | ✅ 재현 (미해결 과제도 함께 재현) |
| 절대 성능 | ❌ 다름 (당연) |
| RQ4 커널 신호 | ⚠️ 여전히 없음 |

**결론**: 계단은 측정 환경의 산물이 아니라 **Spark 메모리 관리자의 성질**이다.
이 재현이 있어야 S1의 결과를 일반화해서 쓸 수 있다.

## 한계

1. 두 점(로컬·EC2)일 뿐이다. 다른 CPU 아키텍처(ARM/Graviton)나 클러스터 모드는 확인 안 됐다.
2. 둘 다 **local 모드**다. executor 간 네트워크 shuffle이 없다.
3. 여전히 `8 GiB · 200 파티션 · 1500m`라는 한 설정이다. 계단의 *위치*는 이 설정에 종속이고, 결과는 *숫자*가 아니라 **"실행 풀 포화가 계단을 만든다"는 구조**다.
