## 결론 먼저

> **커널의 writeback 압력은 비용이 아니다. 디바이스 대역폭은 비용이다 — 단, 넘는 순간에만.**
>
> - `vm.dirty_ratio`를 20% → 2%로 조여 Dirty를 5,952 → 587 MiB로 눌렀는데 **task 시간 변화 ±3.6% 이내** (S5)
> - 같은 job에서 디스크 쓰기를 675 MB/s → 50 MB/s로 조이니 **6.1배 느려짐** (S6, skew 64, lz4)
> - 그런데 **zstd는 1.00배 — 전혀 안 느려졌다**
>
> 규칙: **`job 전체 쓰기량 / bandwidth`** 가 wall time 의 하한을 정한다.
> codec 을 고를 때 봐야 할 것은 spill 이 아니라 **총 쓰기량**이다.

**명제 P5(커널이 cliff을 만든다) → 거짓.** 단, "디스크"로 바꾸면 조건부로 참.

> ⚠️ **2026-09-16 정정.** 아래 §S6 본문은 처음에 규칙을 `spill_bytes / bandwidth` 로
> 썼는데 **지목한 양이 틀렸다.** spill 은 이 job 이 쓰는 양의 23% 에 불과하고
> 나머지는 shuffle write 다. 예측 방향은 맞았지만 이유가 달랐다.
> 본문은 당시 기록 그대로 두고, 무엇이 어떻게 틀렸는지는 맨 아래
> **[정정 (2026-09-16)](#정정-2026-09-16--spill--대역폭-규칙은-틀렸다)** 에 정리했다.
> 본문의 §"메커니즘 — 숨느냐 노출되느냐" 표와 §"예상과 달랐던 것"은 그 정정으로 대체된다.

## S5 — 커널 writeback 압력은 비용이 아니다

### 왜 이 실험이 필요했나

S1·S2·S4 내내 커널 신호가 평탄했다. 하지만 이유가 둘 중 무엇인지 몰랐다:
(a) 커널은 원래 무관하다, (b) 이 규모에서 임계에 안 닿았을 뿐이다.

```
61GB RAM → dirty_background 10% = 6.1GB,  dirty_ratio 20% = 12.2GB
실제 spill 최대                          = 1.24GB
⇒ 근처도 못 갔다
```

그래서 **임계를 spill 양 아래로 끌어내려** 판별했다. Spark 설정은 전부 고정하고 커널 노브 하나만 바꾼 개입 실험이다.

### 개입은 확실히 먹혔다 (positive control)

| `dirty_ratio` | 실효 임계 | peak Dirty | 임계 도달률 |
|---:|---:|---:|---:|
| 20% | 12,474 MiB | 5,952 MiB | 0.48 |
| 8% | 4,981 MiB | 2,371 MiB | 0.48 |
| 2% | 1,234 MiB | **587 MiB** | 0.48 |

Dirty가 임계를 따라 10배 눌렸다. **도달률이 세 조건 모두 정확히 0.48** — 커널이 Dirty를 배경 writeback 임계(하드 임계의 절반) 지점에 계속 묶어두고 있다는 뜻이다.

> 이 표가 없으면 S5의 음성 결과는 무의미하다. "임계를 낮췄는데 아무 일도 없었다"를 주장하려면
> **임계가 실제로 낮아졌고 Dirty가 그에 반응했다**는 증거가 먼저 있어야 한다.

### 그런데 비용은 안 변했다

skew별 max task duration, `dirty_ratio` 20% 대비 변화율:

| skew | 8 | 16 | 32 | 64 |
|---|---:|---:|---:|---:|
| 8% | −0.6% | +0.1% | +1.4% | −0.0% |
| 2% | **−3.6%** | −0.5% | −0.6% | +1.8% |

전부 반복 산포(IQR 0.2~3.2%) 수준이고, 유일하게 유의한 항목은 **오히려 빨라진** 것이다.

### 왜 그런가

`balance_dirty_pages()`의 동기 블로킹이 **한 번도 발동하지 않았다.** 배경 writeback이 Spark의 spill 쓰기 속도(≈75 MB/s)를 NVMe 실력(675 MB/s)으로 여유롭게 따라잡기 때문이다.

**비율을 아무리 조여도 디바이스가 빠르면 스로틀링 자체가 생기지 않는다.**
→ 그래서 다음 실험은 디바이스를 직접 느리게 만드는 것이어야 했다.

## S6 — 디바이스 대역폭은 비용이다, 넘는 순간에만

### 설계

cgroup v2 `io.max`(systemd-run scope)로 **쓰기만** 50 MB/s로 제한.

> 읽기까지 제한하면 8GiB 파케이 스캔이 160초로 늘어나 **"spill이 느린 것"이 아니라
> "입력 읽기가 느린 것"**을 재게 된다. 처음 설계에서 이 실수를 했고 실행 전에 고쳤다.

`io.max`가 실제로 걸렸는지 dd로 검증하고 안 걸렸으면 중단하도록 게이트를 넣었다 (실측 **50.2 MB/s**). 이게 없으면 "디스크는 병목이 아니다"라는 정반대 결론이 나올 수 있다 — `drop_caches` 때와 같은 함정이다.

### 결과: max task duration (ms, median)

| cap | skew | lz4 | zstd | none |
|---|---:|---:|---:|---:|
| 무제한 | 16 | 6,240 | 6,006 | **5,416** |
| 무제한 | 64 | 26,944 | 27,026 | **20,868** |
| 50 MB/s | 16 | 6,328 | 6,036 | **5,403** |
| 50 MB/s | 64 | **164,372** | **27,158** | **158,040** |

느려진 배수 (50 MB/s ÷ 무제한):

| skew | lz4 | zstd | none |
|---|---:|---:|---:|
| 16 | 1.01× | 1.00× | 1.00× |
| **64** | **6.10×** | **1.00×** | **7.57×** |

### 메커니즘 — 숨느냐 노출되느냐

| skew | codec | spill | 50 MB/s 기준 I/O 시간 | 연산 시간 | 결과 |
|---|---|---:|---:|---:|---|
| 16 | lz4 | 137 MiB | 2.7s | 6.2s | **숨겨짐** |
| 16 | zstd | 73 MiB | 1.5s | 6.0s | **숨겨짐** |
| 16 | none | 165 MiB | 3.3s | 5.4s | **숨겨짐** |
| 64 | lz4 | 1,792 MiB | 35.8s | 26.9s | 노출됨 |
| 64 | **zstd** | **954 MiB** | **19.1s** | **27.0s** | **숨겨짐** |
| 64 | none | 2,167 MiB | 43.3s | 20.9s | 노출됨 |

**`spill_bytes / bandwidth` 가 연산 시간보다 짧으면 I/O는 연산 아래로 숨어 공짜다.**
zstd는 lz4의 절반만 쓰기 때문에(954 vs 1,792 MiB) 같은 50 MB/s에서 혼자만 선 아래에 남았다.

### 실무 규칙 — 최적 codec이 뒤집힌다

```
빠른 디스크(675 MB/s)  → 압축을 끄는 게 가장 빠르다
                          none 20.9s  <  zstd 27.0s ≈ lz4 26.9s   (22% 이득)
느린 디스크(50 MB/s)   → 압축을 더 세게 거는 게 가장 빠르다
                          zstd 27.2s  <<  none 158s ≈ lz4 164s    (6배 차이)
```

같은 job, 같은 데이터인데 **디바이스 속도에 따라 정답이 정반대**다.

이것이 Ousterhout et al.(NSDI '15)의 "병목은 대개 CPU"를 보강한다 — 그 결론은
**디스크가 충분히 빠르다는 전제 위에서만** 성립하며, 우리 데이터는 그 전제가 깨지는
지점을 계산 가능한 형태로 준다.

## 예상과 달랐던 것: 비용이 산술보다 훨씬 크게 튄다

산술적으로 lz4 skew 64는 I/O 35.8s vs 연산 26.9s이므로 **최대 35.8s** 정도를 예상했다
(약 1.3배). 실측은 **164s, 6.1배**다.

단순히 "쓰기가 느려서 그만큼 기다린다"가 아니다. 쓰기가 막히면 sorter가 블로킹되고,
그 때문에 spill이 더 자주 일어나고, 다시 I/O가 늘어나는 **되먹임**이 있는 것으로 보인다.

**미검증 가설이다.** 확인하려면 task 단위로 spill 횟수와 blocked 시간을 추적해야 한다
(`results/s6/*/tasks.csv` + `samples.csv`에 원자료는 있다).

# 정정 (2026-09-16) — "spill / 대역폭" 규칙은 틀렸다

위 §S6에서 세운 규칙

> `spill_bytes / bandwidth < compute_time` 이면 I/O는 연산 아래로 숨어 공짜다

는 **지목한 양이 틀렸다.** 예측의 방향(zstd는 숨고 lz4는 노출)은 맞았지만 이유가 다르다.
`results/s6/*/samples.csv`(0.25초 간격 커널 타임시리즈)로 재실행 없이 확인했다.

## 1. spill은 이 job이 쓰는 양의 23%에 불과하다

skew 64 / lz4 기준:

| | |
|---|---:|
| `spill_disk_total` | 1,792 MiB |
| **실제 디스크 출력 (`pgpgout`)** | **7,728 MiB** |

나머지는 **shuffle write**다. `repartition(200, key)`가 데이터셋 전체(8 GiB)를
디스크에 쓴다. 그리고 cgroup `io.max`는 scope의 **모든 쓰기**를 조인다.

```
7,728 MiB / 50 MB/s = 155s   ← 실측 task 162s 와 거의 일치
1,792 MiB / 50 MB/s =  36s   ← 내가 썼던 예측. 실측과 4.6배 차이
```

**"설명 안 되는 6.1배"는 없었다.** 내가 분모에 넣을 양을 잘못 골랐을 뿐이다.

## 2. zstd가 이기는 진짜 이유

| codec | spill (MiB) | **총 쓰기 (MiB)** |
|---|---:|---:|
| lz4 | 1,792 | **7,728** |
| none | 2,167 | **5,808** |
| zstd | 954 | **4,208** |

zstd는 spill만이 아니라 **shuffle write까지 압축한다.** 총 쓰기가 lz4의 54%다.
디바이스가 병목일 때 이기는 건 "spill을 적게 써서"가 아니라 **"전체를 적게 써서"**다.

> `none`이 spill은 제일 많은데(2,167 MiB) 총 쓰기는 lz4보다 적다(5,808 vs 7,728).
> 압축을 끄면 shuffle write는 커져야 하는데 왜 반대인가 — **미해명.**
> `sw_bytes` 를 stage 별로 분해해야 한다. n=1 조건이라 노이즈일 수도 있다.

## 3. task 시간과 wall 시간은 서로 다른 것에 지배된다

cap 50 MB/s:

| skew | codec | n | 총 쓰기 | 무제한 wall → 실측 | 무제한 task → 실측 |
|---|---|---:|---:|---|---|
| 16 | lz4 | 2 | 8,037 | 37.5 → 90.2s | 6.2 → **6.3s** |
| 16 | zstd | 2 | 1,144 | 36.5 → 54.4s | 6.0 → **6.0s** |
| 16 | none | 1 | 3,865 | 30.0 → 102.5s | 5.4 → **5.4s** |
| 64 | lz4 | 2 | 9,768 | 55.3 → 236.1s | 26.9 → **164.4s** |
| 64 | zstd | 1 | 4,351 | 55.3 → 74.1s | 27.0 → **27.2s** |
| 64 | none | 1 | 11,320 | 43.3 → 264.9s | 20.9 → **158.0s** |

**skew 16에서는 wall이 2~3배 늘어도 task는 전혀 안 늘어난다.** 쓰기 backlog가
task가 끝난 뒤에 배수되기 때문이다. 버퍼드 I/O는 비용을 **뒤로 미룬다**.

skew 64에서만 task 자체가 막힌다 — 그리고 그때 막히는 양은 자기 spill(1,792 MiB)이
아니라 **job 전체의 backlog**(9,768 MiB)에 해당한다.

## 4. 타임시리즈: 스톨은 두 덩어리로 온다

`figures/amplification.png` (skew 64 / lz4, capped vs uncapped)

- **17–60s**: PSI io.full = 1.0 (완전 스톨). 이때 dirty는 **0** — page cache가
  흡수하는 게 아니라 쓰기가 bio 레벨에서 직접 막혀 있다.
- 60–105s: 자유 구간. dirty가 6,000 MiB까지 차오른다.
- **107–240s**: 다시 PSI io.full = 1.0. reduce task의 164초가 여기서 나온다.

dirty가 140s경 0으로 빠졌는데도 스톨이 240s까지 이어진다. **이 부분은 아직 설명 못 한다.**

## 5. 그래서 고쳐 쓴 규칙

- ❌ `spill / 대역폭 < 연산시간`
- ✅ **`job 전체 쓰기량 / 대역폭`** 이 wall time 의 하한을 정한다
- ✅ task 가 막히느냐는 별개 문제이고, 막힐 때는 **자기 쓰기가 아니라 job 전체 backlog**를 기다린다
- ✅ codec 을 고를 때 봐야 할 건 spill 이 아니라 **총 쓰기량**이다

## 6. 이 정정이 바꾸지 않는 것

S6의 실무 결론은 그대로다 — 오히려 근거가 더 단단해졌다.

```
빠른 디스크 → 압축 끄기가 22% 빠름     (CPU 가 병목, Ousterhout 재확인)
느린 디스크 → zstd 가 6배 빠름          (총 쓰기량이 병목)
```

다만 **진단 조언이 바뀐다**: "spill 바이트를 보라"가 아니라
**"job이 디스크에 쓰는 총량을 보라"**. Spark UI의 spill 메트릭만 보면 실제 쓰기의
1/4만 보게 된다.

## 7. 남은 숙제

1. `none`의 총 쓰기가 lz4보다 적은 이유 (§2) — stage별 `sw_bytes` 분해 필요
2. dirty가 0인데 스톨이 계속되는 구간 (§4)
3. 위 전부 **n=1~2**다. S6 잔여 15 run + cap 레벨 추가(100·200 MB/s)가 필요하다
