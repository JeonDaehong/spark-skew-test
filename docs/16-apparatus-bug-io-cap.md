# 16. 장치 버그 — io.max가 26%의 run에서 조용히 안 걸렸다

분석: 2026-09-17 · **재실행 없음** (`results/s6v2/*/samples.csv`)

`docs/15`에서 "같은 조건인데 결과가 양봉으로 갈린다"고 썼다. **양봉이 아니었다.
내 실험 장치가 26%의 run에서 조용히 고장나 있었다.**

---

## 증거

skew 64 / lz4 / cap 50 MB/s, 3회 반복:

| rep | 평균 쓰기 속도 | cap 적용? | task |
|---:|---:|---|---:|
| 0 | 84.1 MB/s | ❌ 미적용 | 23.5s |
| 1 | **41.6 MB/s** | ✅ **적용** | **159.2s** |
| 2 | 83.2 MB/s | ❌ 미적용 | 23.3s |

**cap이 실제로 걸린 run에서만 느리다.** 완벽한 상관이다.
"빠른 mode"(23.3~23.5s)는 무제한 run(22.7s)과 **같은 값**이다 — 그냥 제한이 안 걸린 것이다.

적용 실패율은 cap이 낮을수록 높다:

| cap | 적용 | 전체 | 실패율 |
|---:|---:|---:|---:|
| 200 MB/s | 18 | 18 | **0%** |
| 100 MB/s | 13 | 18 | **28%** |
| 50 MB/s | 9 | 18 | **50%** |

## 원인 — 검증이 실제 메커니즘을 테스트하지 않았다

스윕 시작 시 게이트를 넣어뒀었다:

```bash
sudo systemd-run --scope -p "IOWriteBandwidthMax=..." \
  dd if=/dev/zero of=... oflag=direct    # ← direct I/O
```

**`dd oflag=direct`는 direct I/O다.** 발행한 cgroup의 bio 큐를 반드시 통과하므로
항상 스로틀된다(실측 50.2 MB/s로 매번 통과).

**그런데 Spark는 버퍼드 쓰기를 쓴다.** 페이지 캐시에 쓰고 나중에 writeback으로 나간다.
cgroup writeback 귀속은 **io와 memory 컨트롤러가 같은 cgroup에 있어야** 성립한다.
transient scope에 memcg가 위임되지 않으면 writeback이 스로틀을 그냥 통과한다.

> 게이트가 **대용물을 검증**했다. 이건 이 프로젝트에서 세 번째로 같은 계열의 실수다:
> - `drop_caches` 실패를 경고만 하고 넘어감 (→ 중단하도록 고침)
> - AQE 감지를 task 수로 추정 (→ 플랜 마커를 직접 읽도록 고침)
> - io.max를 direct I/O로 검증 (→ 이번 건)
>
> 공통 교훈: **검증은 실험이 의존하는 바로 그 경로를 지나야 한다.**

## 고친 것

**1. run마다 사후 검증** (`runner/run_one.py: _verify_io_cap`)

run 전체 평균 쓰기 속도를 `pgpgout`으로 계산해 cap과 비교한다.
cap의 1.5배를 넘으면 `io_cap_applied=False`로 기록하고 stderr에 경고한다.
`summary.csv`에 `io_cap_applied` / `avg_write_mbps` 컬럼이 생긴다.

**2. cgroup 컨트롤러 함께 위임** (`runner/s6_sweep.sh`)

```bash
sudo systemd-run --scope --uid=ubuntu \
  -p "IOAccounting=yes" -p "MemoryAccounting=yes" \
  -p "IOWriteBandwidthMax=..." ...
```

**3. 스윕 종료 시 적용률 요약 출력** — 미적용 run이 있으면 경고한다.

> 2번이 실제로 문제를 해결하는지는 **다음 실행에서 확인해야 한다.** 미검증이다.
> 해결이 안 되면 1번(사후 검증 + 필터링)으로 최소한 오염된 데이터는 걸러낼 수 있다.

## 걸러내고 나니 물리 법칙이 나왔다

cap이 실제로 걸린 run만 추리면 **lz4는 1/대역폭 법칙을 ±4%로 따른다**:

| codec | cap | n | task_s | 1/대역폭 예측 | 오차 |
|---|---:|---:|---:|---:|---:|
| lz4 | 200 | 3 | 41.0 | (기준) | — |
| lz4 | 100 | 3 | 85.3 | 81.9 | **+4%** |
| lz4 | 50 | 1 | 159.2 | 163.8 | **−3%** |
| none | 200 | 3 | 17.2 | (기준) | — |
| none | 50 | 2 | 77.4 | 69.0 | **+12%** |
| zstd | 200 | 3 | 22.9 | (기준) | — |
| zstd | 100 | 3 | 22.5 | 45.8 | −51% |
| zstd | 50 | 2 | 22.8 | 91.6 | −75% |

또한 cap 100 / lz4는 n=3에서 85.1 / 85.3 / 85.5 — **산포 1.00배**다.
장치가 제대로 작동하면 이 실험은 매우 재현성이 높다.

## 그래서 v1이 맞았다

`docs/15`에서 "v1의 6.1배는 재현되지 않았다"고 철회했는데, **그 철회를 다시 철회한다.**

- v1(21 run)의 6.1배 — cap이 걸린 run을 봤다. **맞다.**
- v2(72 run)의 median 1.04배 — cap이 절반만 걸린 데이터의 중앙값. **틀렸다.**
- `docs/15`의 "양봉 현상" 설명 — 장치 버그를 물리 현상으로 오독한 것. **철회.**

## 아직 설명 못 하는 것

**codec별로 노출되는 대역폭이 다른데, 그 순서가 쓰기량으로 설명되지 않는다.**

| codec | 총 쓰기 (MiB) | spill (MiB) | 노출 시작 |
|---|---:|---:|---|
| lz4 | 9,508 | 1,792 | cap 200에서 이미 |
| none | **11,012** | **2,167** | cap 200~50 사이 |
| zstd | 5,154 | 954 | cap 50에서도 안 됨 |

`none`이 lz4보다 **더 많이 쓰는데 더 늦게** 노출된다. 총 쓰기량으로도, spill 양으로도
순서가 안 맞는다. 쓰기 *패턴*(블록 크기·빈도·타이밍)의 차이일 수 있으나 **미검증이다.**

세 번째로 규칙을 성급히 세우지 않는다. 데이터가 더 필요하다.
