# 11. S2 — bytes인가 records인가: 방법론과 결과

실행: 2026-09-13, EC2 m6id.4xlarge · 90 run · 97분
원자료: `results/s2_ec2/summary.csv` · 그림: `results/s2_ec2/figures/`

---

## 결론 먼저

> **skew의 비용은 바이트가 아니라 레코드로 지불된다.**
>
> ```
> duration_ms = 1741 ns × records + 4.95 ns × bytes − 1602
> R² = 0.9958   (n=90, row width 3종 × skew 6단계 × 5회)
> ```
>
> 레코드 하나가 바이트 하나보다 **352배** 비싸다. 같은 8 GiB를 64B 행으로 담으면 비용의 **88%가 레코드에서** 나오고, 1024B 행으로 담으면 **27%**만 레코드에서 나온다.

그리고 더 놀라운 것:

> **좁은 행은 실행 메모리 풀을 다 쓰지도 못한다.**
> 720 MiB 풀에서 1024B 행은 712 MiB까지 쓰는데, **64B 행은 536 MiB에서 멈춘다.**
> 풀의 **24%가 사용 불가**가 된다.

**명제 P2 → 참.** 계단의 위치는 바이트가 아니라 레코드가 정한다.

---

## 1. 무엇을 물었나

S1은 "계단이 있다"와 "그 계단은 실행 메모리 풀 포화와 일치한다"를 보였다. 풀은 바이트 단위다. 그런데 `UnsafeInMemorySorter`의 `LongArray`는 **record당 16바이트**를 쓴다.

```
총 바이트를 고정한 채 row width만 바꾸면 record 수가 반비례로 변한다.

  bytes가 범인  → 세 곡선의 계단이 같은 skew에 겹친다      (P2 거짓)
  records가 범인 → 좁은 row일수록 계단이 왼쪽으로 이동      (P2 참)
```

---

## 2. 설계

### 통제 / 독립변수

| 항목 | 값 |
|---|---|
| **총 데이터 (고정)** | 8 GiB — 세 row width 전부 **7.96~7.99 GiB** 실측 |
| partitions / cores / exec mem / AQE / codec | 200 / 4 / 1500m / off / lz4 (S1과 동일) |
| **row width (독립)** | 64 · 256 · 1024 B → record 수 **158M · 34.6M · 8.4M** (19배 범위) |
| **skew (독립)** | 8 · 12 · 16 · 20 · 24 · 32 |
| 반복 | 5회 |

### S1에서 발견해 고친 것 2가지

**(a) skew 격자가 너무 성겼다.**
S1은 1·2·4·8·16·32·64였다. peak가 hot 파티션을 따라가다 712 MiB에서 멈추는데, skew 16에서 hot=547·peak=544(여유), skew 32에서 hot=1022·peak=712(포화). 역산하면 **진짜 전이점은 skew ≈ 17**인데 2배 격자로는 "16과 32 사이"까지밖에 못 잡는다.
row width에 따른 이동폭은 계산상 ~26% 예상이었으므로 2배 격자로는 **분해 자체가 불가능**했다. → **8·12·16·20·24·32**로 촘촘하게 바꿨다.

**(b) 총 바이트 통제가 깨져 있었다.**
초기 실행에서 rb=64는 −15.4%, rb=256은 −3.2% — **12.8%p 차이**. parquet의 고정 오버헤드(길이 접두사, 페이지/파일 메타데이터)가 row 폭에 비례하지 않기 때문이다. 이대로면 계단 이동이 row 폭 때문인지 **데이터가 적어서**인지 구분할 수 없다.

→ 생성기에 **실측 캘리브레이션**을 넣었다 (`gen/make_skewed.py`):
1. 작은 샘플을 실제로 써보고 bytes/row를 측정
2. 샘플의 모양을 본 데이터와 일치시킴 — key 분포(상수면 딕셔너리 압축이 과하게 먹음)와 **파일당 행 수**(푸터 오버헤드 비중이 달라짐)
3. 측정값으로 행 수를 역산, 2회 반복 수렴

결과: 오차 스프레드 **12.8%p → 0.9%p** (rb64 −0.85%, rb256 −0.27%, rb1024 +0.05%).

> 둘 다 나중에 발견했으면 S2 전체를 버려야 했다.

## 3. 결과

### (1) 비용 분해 — 핵심

`results/s2_ec2/figures/decompose.png`

hot task의 소요시간을 레코드 항과 바이트 항으로 회귀했다. 총 바이트가 고정돼 있으므로 **두 항은 row width를 통해서만 분리된다** — S2 설계가 있어야만 가능한 분해다.

```
duration_ms = 1741.46 ns × records + 4.95 ns × bytes − 1602 ms
R² = 0.9958   (n=90)
```

row width 3종이 **하나의 모델로 전부 설명된다** (그림 A의 y=x 위에 세 색이 모두 올라감).

| row width | records | bytes | record항 | byte항 | **record 비중** |
|---|---:|---:|---:|---:|---:|
| 64 B | 13,040,106 | 611 MiB | 22,709 ms | 3,176 ms | **87.7%** |
| 256 B | 2,851,398 | 629 MiB | 4,966 ms | 3,268 ms | **60.3%** |
| 1024 B | 691,278 | 633 MiB | 1,204 ms | 3,286 ms | **26.8%** |

byte항은 세 경우 모두 ~3,200 ms로 거의 같다 (바이트가 고정이니 당연). **차이는 전부 record항에서 나온다.**

> **정직한 한계**: 상수항이 −1602 ms로 음수다. 물리적 의미가 없으며, 실제 관계가 약간 볼록(spill 이후 가속)한데 선형으로 근사했기 때문이다. 이 모델은 측정 범위 안에서의 국소 선형화이지 외삽용이 아니다.

### (2) 실행 메모리 풀의 천장 높이가 row width마다 다르다

`results/s2_ec2/figures/row_width.png` 패널 B

| row width | peak 천장 | 풀(720 MiB) 대비 | 천장 유지 구간 |
|---|---:|---:|---|
| 64 B | **536.0 MiB** (562,035,920 B) | **74%** | skew 12~32 |
| 256 B | 712.0 MiB (746,584,816 B) | 99% | skew 20~32 |
| 1024 B | 712.0 MiB (746,584,720 B) | 99% | skew 24~32 |

넓은 행은 풀을 거의 다 쓴다(712/720 = 99%). **좁은 행은 536 MiB에서 멈춘다 — 176 MiB, 즉 풀의 24%를 쓰지 못한다.**

가장 그럴듯한 메커니즘은 `LongArray`의 **2배 성장**이다. 포인터 배열을 키우려면 다음 크기를 통째로 할당해야 하는데, 좁은 행에서는 배열이 커서 한 번 더 배증하면 풀을 넘긴다 → 할당 실패 → spill. 그래서 데이터가 풀을 채우기 전에 천장에 닿는다.

> **미검증.** 이건 관측과 정합적인 가설이지 증명이 아니다. **S3/S4에서 `LongArray` 할당을 직접 추적해 확인해야 한다** (async-profiler 또는 `UnsafeExternalSorter` 계측). 확인 전까지 블로그에 단정해서 쓰지 않는다.

### (3) 계단의 위치가 이동한다

| row width | 실행 풀 포화 skew | ms/MB 계단 | 계단 크기 | IQR 대비 |
|---|---:|---|---:|---:|
| 64 B | **12** | skew 8 → 20 (33.44 → 40.96) | **+22%** | 7배 |
| 256 B | **20** | skew 12 → 24 (8.93 → 11.40) | **+28%** | 11배 |
| 1024 B | **24** | skew 20 → 24 (3.71 → 7.10) | **+91%** | 5배 |

**포화 지점이 12 → 20 → 24로 단조 이동한다.** 예측은 ~26% 이동이었는데 실제로는 **2배** 이동했다 — 포인터 배열의 메모리 점유뿐 아니라 **천장 높이 자체가 낮아지기** 때문이다.

계단 크기는 전부 반복 산포(IQR)의 5~11배로, 노이즈가 아니다.

### (4) spill이 같은 이야기를 한다

skew별 spill to disk (MiB, median):

| skew | rb=64 | rb=256 | rb=1024 |
|---:|---:|---:|---:|
| 8 | 124 | 137 | 155 |
| 12 | **368** | 137 | 155 |
| 16 | 368 | 137 | 155 |
| 20 | **611** | 137 | 155 |
| 24 | 652 | **687** | **793** |
| 32 | 895 | 687 | 793 |

rb=64는 skew 12부터 spill이 오르기 시작하고, rb=256/1024는 skew 24까지 평탄하다가 급증한다. 포화 지점과 정확히 일치한다.

S1의 수수께끼였던 **고정 배경 spill도 재현**됐다 (rb=256에서 137 MiB — S1의 136.5 MiB와 동일). 다만 row width에 따라 124 / 137 / 155로 약간 달라진다. **여전히 미해결.**

## 4. 이게 왜 중요한가 — P3로 직결된다

`docs/00-research-triage.md`의 명제 P3:

> **AQE는 record-skew를 감지하지 못한다** (판정이 byte 전용이므로)

S2가 이 명제에 힘을 실어준다. AQE의 skew 판정은 `ShufflePartitionsUtil`에서 `bytesByPartitionId`만 본다 — **바이트만 본다.** 그런데 지금 측정으로:

- 비용의 지배 요인은 **레코드**다 (좁은 행에서 88%)
- 레코드 하나는 바이트 하나보다 **352배** 비싸다
- 좁은 행은 실행 메모리 풀조차 **24% 덜** 쓴다

⇒ **바이트로는 평범해 보이지만 레코드가 몰린 파티션은 AQE에 안 잡히면서 실제로는 4배 비싸다.**

이것이 S4에서 직접 검증할 대상이고, 참이면 Spark JIRA / dev@ 논의 후보다.

> 다만 `04-novelty-risk.md`의 원칙을 지킨다: AQE가 byte 기반인 건 소스를 읽으면 보인다. 정직한 표현은 *"새로 발견했다"*가 아니라 ***"알려질 수 있었지만 아무도 측정해서 보여주지 않은 것을 측정했다"***.

## 5. 한계

1. **단일 환경 · 단일 워크로드.** m6id.4xlarge, local[4], sort 워크로드. join/aggregation 일반화는 S8.
2. **1741 ns/record는 이 조건의 값**이다. CPU·정렬 키·직렬화기가 바뀌면 달라진다. 결과는 *숫자*가 아니라 **"레코드 항이 바이트 항을 압도한다"는 구조**다.
3. **천장 536 MiB의 메커니즘은 가설**이다 (§3-2). `LongArray` 배증을 직접 추적하기 전까지 단정하지 않는다.
4. **상수항이 음수**다 (§3-1). 모델은 측정 범위 내 국소 선형화다.
5. row width 3점만으로 회귀했다. 중간 폭(128, 512)을 넣으면 더 단단해진다.
6. **커널 레이어는 여전히 조용하다.** PSI io.full이 4.6~6.6s로 skew·row width와 무관하게 평탄. RQ4는 아직 신호 없음 — S5/S6에서 RAM 제한과 `vm.dirty_ratio`로 강제해야 한다.
