## 0. 왜 세 번이나 다시 했나

S6 의 질문은 단순했다. **디스크가 느려지면 skew 비용이 비선형으로 커지는가?**
cgroup v2 의 `io.max` 로 쓰기 대역폭을 인위적으로 조이고 시간을 재면 될 일이었다.

그런데 세 번 다 다른 답이 나왔다.

| | run | 결론 | 무엇이 틀렸나 |
|---|---:|---|---|
| v1 | 21 | "대역폭을 절반으로 줄이면 6.1배" | 분모를 잘못 골랐다 (spill 이 아니라 총 쓰기량) → docs/13 에서 정정 |
| v2 | 72 | "재현 안 됨, median 1.04배" | cap 이 **26% 의 run 에서 안 걸려 있었다** → docs/16 |
| v3 | 36 | 아래 §2 | — |

v3 는 v2 의 장치 버그를 고치고 다시 돌린 것이다. 고친 것:

- 검증 기준을 시스템 전체 `pgpgout` 에서 **자기 cgroup 의 `io.stat` wbytes** 로 교체
  (앞 run 의 잔여 writeback 이 섞이지 않는다)
- run 마다 `io_cap_applied` / `cgroup_write_mbps` 를 기록
- median 뿐 아니라 min/max 를 같이 본다 (v2 에서 median 이 양봉을 뭉갰다)

## 2. 무엇을 알게 됐나

### (1) cap=50 에서는 계기가 제대로 작동한다

lz4 cap=50 의 6 run 모두 cgroup 실측이 **40.8~46.2 MiB/s** (선언 50). wall 은
217~239s 로 퍼짐이 1.10× 밖에 안 된다. 이건 깨끗한 개입이다.
그리고 무제한 44.1s → 50MB/s 236.5s 는 **5.4배** — 디스크를 충분히 조이면
skew 비용이 폭발한다는 것 자체는 사실이다.

### (2) cap≥100 에서는 계기가 무너진다

lz4 cap=100 의 run 별 cgroup 실측:

```
cgroup 238.8 MiB/s → wall  37.0s   (선언 100 의 2.4배. cap 이 안 걸렸다)
cgroup 238.1 MiB/s → wall  37.2s
cgroup 155.6 MiB/s → wall  57.7s
cgroup 138.0 MiB/s → wall  56.7s
cgroup 112.8 MiB/s → wall  69.0s
cgroup  76.4 MiB/s → wall 126.3s
```

같은 명령으로 같은 cap 을 걸었는데 실제 대역폭이 **76~239 MiB/s, 3배** 벌어진다.
그리고 wall 은 그 실측 대역폭을 충실히 따라간다 (76 → 126s, 239 → 37s).
**즉 시간은 우리가 선언한 cap 이 아니라 디스크가 실제로 내준 대역폭이 정한다.**

### (3) `io_cap_applied=True` 도 믿을 수 없다

lz4 cap=200 은 6/6 이 "적용됨"으로 찍혔다. 그런데 실측은:

```
237.7 / 235.0 / 220.6  MiB/s → wall 36.9 / 37.3 / 39.6 s
119.3 / 112.9 / 111.6  MiB/s → wall 66.6 / 76.8 / 77.6 s
```

셋은 선언 cap 200 을 **넘겼는데도** 통과했다. `_verify_io_cap` 의 허용치가
1.5배라서 cap=200 이면 300 MiB/s 까지 통과시킨다 — 이 장비의 최대 쓰기 속도보다
높다. **cap=200 에서 이 검사는 원리적으로 실패할 수 없다.** 검증이 아니라 장식이었다.

zstd cap=50 도 같은 문제다. 3/3 통과했지만 하나는 66.3 MiB/s (선언 50 초과)로
63.6s 에 끝났고 나머지 둘은 35 MiB/s 로 143~148s 걸렸다. "퍼짐 2.34×" 의 정체다.

### (4) 진짜 원인은 장비 쪽 양봉이다

cap=200 의 실측이 `~230` 과 `~115` 두 무리로 갈린다. 중간값이 없다.
cap=100 도 `~238` 과 `~76~155`. instance-store NVMe 가 **run 마다 2배 차이나는
쓰기 대역폭**을 내주고 있고, `io.max` 는 천장만 내릴 뿐 바닥을 올리지 못한다.
우리가 걸려는 조작(2배)과 장비 자체의 분산(2배)이 같은 크기라 분리가 안 된다.

## 3. 판정

| | |
|---|---|
| **"디스크가 느려지면 skew 비용이 커진다"** | ✅ 참 — 단, **충분히 느릴 때만**. 50 MB/s 에서 5.4배 |
| **"대역폭 절반 → 시간 2배" 같은 깔끔한 법칙** | ❌ **측정 불가.** 이 하네스/하드웨어로는 확인할 수 없다 |
| **cgroup `io.max` 의 계기로서의 유효 범위** | 이 장비에서 **~50 MB/s 이하에서만** 신뢰할 수 있다 |
| v1 의 "6.1배" | 철회 유지 (docs/13) |
| v2 의 규칙 2건 | 철회 유지 (docs/15) |

**S6 는 여기서 닫는다.** 더 돌려도 같은 벽에 부딪힌다. 제대로 하려면 장비를
바꿔야 한다 — 대역폭이 안정적인 EBS gp3(provisioned IOPS/throughput)로 가거나,
`fio` 로 사전에 장비 분산을 측정해 그보다 훨씬 작은 조작은 시도하지 않는 것.

## 4. 남기는 교훈

> **개입 실험에서 "개입이 걸렸다"는 검사는 개입 자체보다 먼저 검증해야 한다.**
> 나는 세 번에 걸쳐 (a) 분모를 잘못 고르고 (b) 검사가 아예 안 걸린 걸 모르고
> (c) 검사의 허용치가 너무 넓어 무조건 통과하는 걸 모르고 결론을 냈다.
> 세 번 다 **데이터는 멀쩡했고 계기가 고장나 있었다.**

> **조작량은 장비의 자연 분산보다 확실히 커야 한다.**
> 2배를 조작하는데 장비가 알아서 2배 흔들리면 아무것도 못 잰다.
> 이걸 먼저 재봤어야 했다. 129 run 을 쓰고 나서야 알았다.

`analysis/s6_bandwidth_law.py` 는 "cap 이 실제로 걸린 run 만 사용"하도록
짜여 있다. 남겨두되, 위 §2(3) 때문에 **그 필터 자체가 cap≥100 에서는 못 믿는다**는
점을 기억할 것.
