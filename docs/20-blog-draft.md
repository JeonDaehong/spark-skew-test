# 태스크 하나 때문에 잡이 안 끝날 때, 진짜 범인은 누구인가

> 블로그 초안 v2 (쉬운 버전) · 2026-09-18
> 근거: `results/` 원자료 449 run, 상세는 `docs/10~16`

---

## 겪어본 상황

Spark UI를 연다. 스테이지 하나가 안 끝나고 있다.

태스크 200개 중 199개는 30초 만에 끝났는데, **하나가 혼자 24초째가 아니라 24분째** 돌고 있다. 데이터가 특정 키에 몰린 것이다. 흔히 말하는 skew다.

여기까지는 다들 안다. 보통 이렇게 한다 — AQE를 켠다, 파티션을 늘린다, salting을 한다, executor 메모리를 올린다.

그런데 이 중에 **뭘 해야 하는지**는 어떻게 정하나?

나는 그게 궁금했다. 정확히는 이 두 가지가.

1. **언제부터** 느려지기 시작하나? 조금씩 나빠지나, 아니면 어느 순간 훅 꺾이나?
2. 그 지점을 **누가** 정하나? Spark 설정인가, JVM인가, 리눅스인가, 디스크인가?

2번이 중요한 이유는 간단하다. 범인이 누구냐에 따라 손댈 곳이 완전히 달라진다. Spark 설정이면 config를 고치면 되고, 디스크면 인스턴스 타입을 바꿔야 한다. 엉뚱한 데를 고치면 돈만 쓰고 안 낫는다.

---

## 어떻게 알아봤나

말로 답하는 대신 재보기로 했다.

핵심은 **데이터 총량을 고정**하는 것이다. 8GB짜리 데이터를 만들되, 한 키에 몰리는 정도(skew)만 1배에서 64배까지 바꿨다. 총량이 같으니 "데이터가 많아서 느린 것"과 "쏠려서 느린 것"이 섞이지 않는다.

그리고 **꺾이는 지점이 어디로 움직이는지**를 봤다. 행 폭을 바꾸면 그 지점이 움직이나? CPU 코어 수를 바꾸면? 리눅스 설정을 건드리면? 디스크를 느리게 만들면?

움직이면 그게 범인이다.

EC2 전용 인스턴스에서 총 **449번** 돌렸다. 매번 페이지 캐시를 비우고, 같은 조건을 3~5회 반복하고, 편차를 전부 기록했다. 총 비용은 약 $5였다.

> 참고로 워크로드는 `groupBy().count()`를 쓰면 안 된다. Spark가 똑똑해서 개수 세기는 mapper 단계에서 미리 접어버린다. 쏠린 키가 mapper당 1행으로 줄어들어서 **skew 효과 자체가 사라진다.** 그래서 정렬 작업을 썼다. 정렬은 못 접는다.

## 발견 1 — 서서히가 아니라, 계단이다

먼저 raw 숫자를 보면 오해하기 쉽다. skew를 1에서 64로 키우니 느린 태스크가 2.3초 → 24초, 10배가 됐다. 그런데 쏠린 파티션 크기도 54MB → 1,798MB로 33배 커졌다. **커졌으니까 오래 걸린다. 당연하다.**

그래서 나눠봤다. **1MB를 처리하는 데 몇 밀리초 걸리나?**

| skew | 8배 | 16배 | 32배 | 64배 |
|---|---|---|---|---|
| 1MB당 걸린 시간 | 10.0ms | 10.4ms | **13.6ms** | 13.6ms |

- skew 8~16: 10.2ms — **평평하다**
- skew 32~64: 13.6ms — **여기도 평평하다**
- 그 사이에 **한 번, 31% 계단**

반복 측정 편차가 0.5ms 수준인데 계단이 3.2ms다. **노이즈의 40배**니까 우연이 아니다.

즉 데이터가 쏠릴수록 조금씩 나빠지는 게 아니다. **어느 선까지는 멀쩡하다가, 선을 넘으면 한 번 확 비싸지고, 그 뒤로는 또 평평하다.**

### 그 선이 어디인지 계산할 수 있다

계단이 생긴 지점에서 뭐가 일어났는지 봤더니 명확했다.

Spark는 정렬 같은 작업에 쓰는 **작업용 메모리 풀**이 따로 있다. 내 설정에서는 720MB였다. 쏠린 파티션이 이 안에 들어가면 메모리에서 정렬이 끝난다. 안 들어가면 디스크로 흘려보내야 한다(spill).

| skew | 쏠린 파티션 | 실제로 쓴 작업 메모리 |
|---|---|---|
| 16배 | 547MB | 544MB (아직 여유) |
| **32배** | 1,022MB | **712MB ← 천장에 닿음** |
| 64배 | 1,798MB | **712MB (고정)** |

712MB에서 멈춘다. 720MB 풀의 99%다. 여기서부터 넘치는 만큼 디스크로 나가고, 1MB당 비용이 그 순간 한 번 뛴다.

**그러니까 계단 위치는 계산할 수 있다.** 작업 메모리 풀 크기를 파티션 크기로 나누면 대충 어디서 꺾일지 나온다.

### 이게 내 노트북 얘기가 아니라는 증거

같은 실험을 두 군데서 돌렸다. 하나는 내 데스크톱(Ryzen + WSL2), 하나는 EC2(Xeon + 진짜 NVMe). CPU도 디스크도 OS도 다르다.

그런데 "실제로 쓴 작업 메모리" 값이 **MB 단위까지 똑같이 나왔다** — 72 / 96 / 176 / 184 / 544 / 712 / 712.

이 천장은 하드웨어가 아니라 **Spark의 메모리 관리자가 정하는 값**이라는 뜻이다.

## 발견 2 — 용량이 아니라 '줄 수'가 문제다

여기서부터가 덜 알려진 부분이다.

작업 메모리 풀은 **바이트** 단위다. 그런데 Spark가 정렬할 때는 데이터만 담는 게 아니다. **행마다 16바이트짜리 '주소표'를 따로 만든다.** 어떤 행이 어디 있는지 가리키는 포인터다.

그러면 이런 일이 생긴다. 같은 1GB라도

- 행이 넓으면(1KB) → 100만 행 → 주소표 16MB
- 행이 좁으면(64B) → 1600만 행 → 주소표 **256MB**

**같은 용량인데 주소표만 16배 차이 난다.**

확인해봤다. 총량을 8GB로 고정하고 행 폭만 64B / 256B / 1KB로 바꿔서 행 수를 19배 흔들었다. 90번 측정해서 식을 뽑으니 이렇게 나왔다.

```
걸린 시간 = 1,741ns × (행 수)  +  4.95ns × (바이트 수)
R² = 0.996
```

**행 하나가 바이트 하나보다 352배 비싸다.**

같은 8GB인데 비용 구성이 이렇게 갈린다.

| 행 폭 | 행 수 | 비용 중 '행' 몫 |
|---|---|---|
| 64B | 1,300만 | **88%** |
| 256B | 285만 | 60% |
| 1KB | 69만 | **27%** |

바이트 몫은 셋 다 똑같다(바이트를 고정했으니까). **차이가 전부 행 수에서 나온다.**

### 덤: 좁은 행은 메모리를 다 쓰지도 못한다

더 재밌는 게 나왔다. 720MB 풀에서

- 1KB 행 → 712MB까지 씀 (99%)
- 256B 행 → 712MB (99%)
- **64B 행 → 536MB에서 멈춤 (74%)**

같은 설정인데 좁은 행에서는 **풀의 4분의 1을 못 쓴다.** 주소표가 2배씩 커지는 구조라서, 한 번 더 늘리면 풀을 넘겨버려 데이터가 다 차기도 전에 디스크로 밀려나는 것으로 보인다.

> 이건 관측과 앞뒤가 맞는 설명이지 증명은 아니다. 확정하려면 Spark 내부 할당을 직접 추적해야 한다.

## 발견 3 — 그래서 AQE는 이걸 못 본다 (제일 실용적인 부분)

AQE(Adaptive Query Execution)는 Spark 3부터 들어간 기능이다. 쏠린 파티션을 자동으로 감지해서 잘게 쪼개준다. skew 문제의 표준 처방이다.

그런데 AQE가 **어떻게 감지하는지** 소스를 열어봤다.

```scala
val leftMedSize = Utils.median(leftSizes, false)   // ← bytesByPartitionId
val isLeftSkew  = leftSize > leftSkewThreshold
```

**바이트만 본다. 행 수는 어디에도 없다.**

발견 2와 합치면 예측이 나온다. *"용량은 평범한데 행이 몰린 파티션"* 은 AQE 눈에 안 보이면서 실제로는 비쌀 것이다.

그래서 그런 데이터를 만들었다. 쏠린 키에는 좁은 행을, 나머지 키에는 넓은 행을 줘서 **파티션당 용량은 거의 같고 행 수만 최대 64배** 차이 나게.

결과:

| | 조건 수 | AQE가 감지했나 |
|---|---|---|
| 용량이 쏠린 경우 (평범한 skew) | 3 | **3번 다 감지** ✅ |
| 행 수만 쏠린 경우 | 6 | **한 번도 감지 못 함** ❌ |

플랜에 남는 표시로 직접 확인했다. 용량 쏠림은 `SortMergeJoin ... skew=true`가 붙는데, 행 쏠림은 안 붙는다.

### 그리고 방치된 쪽이 더 느렸다

```
용량 쏠림   AQE가 쪼갬   6.3초 → 1.6초   (4배 개선)
행 쏠림     AQE 무반응   3.5초 → 3.6초   (변화 없음)
```

**AQE가 고쳐준 파티션(1.6초)보다, 무시한 파티션(3.6초)이 2배 넘게 느리다.**

AQE가 무능한 게 아니다. 용량 쏠림에는 압도적으로 잘 듣는다 — 심한 경우 19초를 1.1초로 줄였다. **17배다.** 단지 **행 쏠림은 보지를 못한다.**

> **실무 조언**: AQE를 켰는데도 느린 태스크가 남아 있으면, 파티션의 **행 수**를 보자.
> Spark UI에서 크기만 보면 "다 비슷한데?" 하고 넘어가게 된다.

정직하게 덧붙이면, "AQE가 바이트만 본다"는 지적은 이미 몇몇 글에 있다. 소스를 읽으면 보이기도 한다. 내가 한 건 **그게 실제로 얼마나 비싼지 재본 것**이다.

## 발견 4 — 리눅스는 범인이 아니었다. 디스크는 '충분히 느릴 때만' 범인이다

처음에 나는 이런 그림을 그렸다.

> 메모리가 모자라 디스크로 흘린다 → 리눅스 페이지 캐시에 쌓인다 → 캐시가 차면 커널이 쓰기를 막는다 → 태스크가 멈춘다

그럴듯했고, 실험 계획의 절반이 여기 걸려 있었다. 커널까지 파고드는 게 이 프로젝트의 목표이기도 했다.

그래서 리눅스 설정(`vm.dirty_ratio`)을 20% → 2%로 조였다. 커널이 훨씬 일찍, 훨씬 공격적으로 디스크에 밀어내게 만든 것이다.

**개입은 확실히 먹혔다.** 캐시에 쌓인 양이 5,952MB → 587MB로 10분의 1이 됐다.

**그런데 잡 시간은 안 변했다.** 전 구간에서 ±3.6% 이내. 반복 편차 수준이다. 유일하게 통계적으로 유의한 항목은 오히려 **빨라진** 거였다.

이유는 싱거웠다. 커널이 태스크를 막는 상황이 **한 번도 안 생겼다.** Spark가 디스크에 쓰는 속도가 초당 75MB 정도인데 NVMe는 초당 675MB를 쓴다. 커널이 여유롭게 따라잡는다. 설정을 아무리 조여도 **디스크가 빠르면 애초에 막힐 일이 없다.**

음성 결과지만 이게 없었으면 "커널이 뭔가 하고 있을 것"이라는 막연한 의심이 계속 남았을 것이다.

### 디스크를 진짜로 느리게 만들어봤다 — 절반만 성공했다

그럼 디스크가 느리면? 리눅스 cgroup으로 쓰기 속도에 상한을 걸어봤다.

**초당 50MB로 조였을 때는 답이 깨끗하게 나왔다.**

```
제한 없음   44초
50MB/s     237초     ← 5.4배
```

6번 돌려서 217~239초. 거의 안 흔들린다. 디스크가 충분히 느리면 skew 비용이 폭발하는 건 사실이다.

**문제는 그 위였다.** 100MB/s로 걸었을 때, 6번 돌린 실제 쓰기 속도가 이랬다.

```
실제 239MB/s → 37초    ← 상한이 아예 안 걸렸다
실제 156MB/s → 58초
실제 113MB/s → 69초
실제  76MB/s → 126초
```

같은 명령으로 같은 상한을 걸었는데 **실제 속도가 3배 벌어진다.** 그리고 걸린 시간은 내가 선언한 상한이 아니라 디스크가 그때그때 실제로 내준 속도를 따라간다.

원인은 Spark가 아니라 **장비**였다. 이 NVMe는 실행할 때마다 76~239MB/s 사이에서 널뛴다. 내가 걸려던 조작이 "2배 느리게"인데 장비가 알아서 2배씩 흔들리니, 둘을 분리할 방법이 없다.

> **조작하려는 양은 장비가 알아서 흔들리는 양보다 확실히 커야 한다.**
> 이걸 먼저 재봤어야 했는데, 129번을 돌리고 나서야 알았다.

절반은 건졌다. "느린 디스크 + skew = 재앙"은 확인했고(5.4배), "대역폭 절반이면 시간 두 배" 같은 깔끔한 법칙은 **이 장비로는 못 잰다**가 결론이다.

다만 세 번의 시도가 **한 가지에는 다 일치했다.**

```
빠른 NVMe에서는 압축을 끄는 게 가장 빠르다
  압축 없음 17.7초  <  lz4 22.5초 ≈ zstd 23.4초
```

압축은 CPU를 써서 디스크 I/O를 아끼는 거래다. 디스크가 충분히 빠르면 **그 거래가 손해**다.

## 발견 5 — 흔한 튜닝 조언이 맞긴 맞는데, 이유가 틀렸다

이런 조언을 많이 본다.

> executor 하나에 core를 많이 주면, 태스크마다 쓸 수 있는 메모리가 1/N로 쪼개진다.
> 그러니 core를 줄여라.

core를 1, 2, 4, 6으로 바꿔가며 48번 돌렸다. 메모리는 고정, 데이터도 고정.

**결론부터: 예측은 맞고 설명은 틀렸다.**

### 메모리는 1/N로 안 쪼개진다

hot 태스크가 실제로 잡은 메모리 최대치다. 전체 풀은 720MB.

| core 수 | 조언의 예측 | 실측 |
|---:|---:|---:|
| 1 | 720MB | 704MB |
| 2 | 360MB | 704MB |
| 4 | 180MB | 712MB |
| 6 | **120MB** | **716MB** |

core를 6개 줘도 태스크 하나가 **716MB를 다 쓴다.** 조언의 예측치보다 6배 많다.

당연하다. 파티션 200개 중 큰 건 하나뿐이고, 나머지 199개는 금방 끝나서 자리를 비켜준다. "1/N"은 **최소한 이만큼은 보장한다**는 뜻이지 **이만큼만 준다**는 뜻이 아니다.

### 그런데 디스크로 뱉기 시작하는 지점은 진짜로 앞당겨진다

| core 수 | 디스크로 쏟아내기 시작하는 skew |
|---:|---:|
| 2 | 32 |
| 4 | 24 |
| 6 | **20** |

조언의 결론은 맞았다. 그럼 왜?

**core 수는 최대치를 정하는 게 아니라, 첫 번째로 흘러넘치는 시점을 정한다.**

처음엔 모든 태스크가 동시에 돌고 있으니 각자 1/N만 보장받는다. hot 태스크는 그 몫을 채우자마자 한 번 디스크로 뱉는다. 그 첫 번째 방출량이 이랬다.

```
core 1 →  544MB
core 2 →  272MB   (544의 1/2)
core 4 →  136MB   (544의 1/4)
core 6 →   85MB   (544의 1/6)
```

**정확히 1/N이다.** 그것도 두 번 돌린 결과가 바이트 단위로 똑같이 나온다.

한 번 비우고 나면 그때부터는 풀 전체를 쓸 수 있다. 그래서 최대치는 716MB가 된다. core가 많을수록 **첫 방출이 적어서, 비우고 난 뒤 남은 여유가 적다.** 그래서 더 일찍 한계에 부딪힌다.

### 실무로 옮기면

- **"core를 줄이면 메모리 압박이 준다"는 반만 맞다.** 줄어드는 건 한계에 닿는 지점이지 최대 사용량이 아니다. hot 태스크는 몇 core든 풀을 다 쓴다.
- **core를 늘릴 때 executor 메모리를 같이 늘려야 하는 진짜 이유는 spill이 아니라 OOM이다.** 48번 중 2번이 죽었는데 둘 다 core 6이었다. Spark의 메모리 풀은 720MB를 잘 지켰는데 **힙이 터졌다.** 풀이 관리하지 않는 버퍼들이 core 수에 비례해서 늘기 때문이다.
- **skew는 코어를 더 붙여서 해결할 수 없다.** 같은 데이터, 같은 설정에서 6 core의 속도 향상이 이랬다.

```
skew 8  →  4.23배
skew 32 →  3.23배    ← 24%가 그냥 날아간다
```

코어를 더 사도 skew가 심하면 수익률이 떨어진다.

## 발견 6 — 이게 정렬에서만 나오는 얘기인가?

여기까지 읽고 이런 생각이 들 수 있다. 전부 **정렬(sort)** 작업에서 나온 숫자다. 조인이나 집계에서도 같은 일이 벌어지나?

확인해봤다. 같은 데이터, 같은 메모리로 네 가지 작업을 99번 돌렸다.

- **sort** — 지금까지 쓴 그 작업
- **join** — SortMergeJoin
- **agg** — `collect_list`로 모으는 집계
- **count** — 그냥 세기. **여기서는 아무 일도 안 일어나야 한다**

`count`를 넣은 게 핵심이다. 세기만 하는 작업은 Spark가 셔플 **전에** 각 노드에서 미리 세버린다. 그래서 큰 파티션 자체가 안 생긴다. **여기서까지 느려지면 지금까지의 설명이 틀린 것이다.**

### 결과: 법칙은 같고, 숫자는 다르다

skew를 8에서 32로 올렸을 때:

| 작업 | 걸린 시간 | 메모리 최대치 |
|---|---|---|
| sort | 30.8 → 38.1초 | 197 → **712MB** |
| join | 25.9 → 29.6초 | 245 → **616MB** |
| count | 5.5 → **5.4초** | 8 → **8MB** |

**`count`는 완전히 평평하다.** 5.5초에서 5.4초. 메모리도 8MB에서 안 움직인다. 예상대로 셔플 전에 다 흡수해버렸다. 설명이 반증되지 않았다.

**join은 sort와 똑같이 계단을 밟는다.** 넘어가는 지점(skew 16과 24 사이)도 같다.

**그런데 천장이 다르다.** sort는 712MB에서 멈추고 join은 616MB에서 멈춘다. 100MB 일찍 넘친다. 이 값은 6번씩 돌려서 **소수점까지 똑같이** 나왔다. 우연이 아니다.

왜 그런지는 짐작만 한다. SortMergeJoin은 한 작업 안에서 **양쪽을 각각 정렬한다.** 메모리를 쓰는 주체가 둘이라 하나가 전부를 가져가지 못한다. 직접 확인하지는 못했다.

### 아까 그 "1/N" 도 그대로다

발견 5에서 첫 방출량이 core 수의 1/N로 줄어든다고 했다. join에서도 똑같다.

```
join의 첫 방출량 x core 수
  1 core  462.8MB
  2 core  462.8MB
  4 core  462.8MB    ← 소수점까지 동일
```

**1/N은 그대로인데 상수가 다르다.** sort는 풀의 75.7%에서 처음 넘치고, join은 64.3%에서 넘친다.

> 이게 이 실험의 결론이다. **법칙은 옮겨가고 숫자는 안 옮겨간다.**
> "메모리 풀의 76%쯤에서 처음 넘친다"는 sort에서 잰 값이다.
> 다른 작업에 그대로 가져다 쓰면 틀린다.

### 집계는 답을 못 얻었다

`agg`는 시간이 22.2초에서 22.3초로 아예 안 움직였다. 그런데 이걸 "집계는 skew에 강하다"로 읽으면 안 된다. **두 가지가 겹쳐서 측정 자체가 안 됐다.**

1. `collect_list(substring(payload, 1, 8))`이라 셔플 양이 20분의 1로 줄었다. 애초에 메모리 풀 근처에 못 갔다.
2. Spark가 이 작업의 메모리 사용량을 **아예 보고하지 않는다.** 모든 실행에서 정확히 0으로 찍힌다. "안 썼다"가 아니라 "안 보인다"다.

집계를 제대로 재려면 다른 계측이 필요하다. 못 한 걸 못 했다고 적어둔다.

## 내가 틀린 것들

여기부터는 결과가 아니라 과정이다. 그런데 나한테는 이게 제일 남았다.

### 1. 반올림이 없는 패턴을 만들어냈다

집계표에서 skew 4·8·16이 **전부 정확히 136.5MB**를 디스크로 흘렸다. 네 번의 실험에 걸쳐 똑같이 나왔다. "뭔가 고정된 값이 있다"고 기록하고 수수께끼로 남겼다.

나중에 raw 값을 봤다.

```
143,173,819  /  143,167,339  /  143,161,152 바이트
```

**다 다른 값인데 MB로 반올림하니 같아 보였던 것이다.** 나는 이걸 네 번이나 "재현되는 패턴"이라고 적었다.

태스크 단위로 내려가 보니 "고정"도 아니었다. 디스크로 흘린 태스크는 **200개 중 딱 하나**, 쏠린 파티션이었다.

> **집계표에서 자릿수를 줄이면 없던 패턴이 생긴다.** 이상하게 딱 떨어지는 값을 보면 raw를 확인하자.

### 2. 검증이 엉뚱한 걸 테스트했다

디스크를 느리게 만드는 실험에서, "제한이 진짜 걸렸나"를 확인하는 장치를 넣었다. `dd`로 파일을 쓰면서 속도를 재는 거였다.

매번 통과했다. 그런데 나는 `dd`에 **direct I/O** 옵션을 줬고, **Spark는 버퍼드 쓰기를 쓴다.** 둘은 커널 안에서 다른 길로 간다.

**검증이 실험이 실제로 쓰는 길을 안 지난 것이다.**

이 프로젝트에서 같은 실수를 네 번 했다.

| 뭘 | 어떻게 틀렸나 |
|---|---|
| 캐시 비우기 | 실패해도 경고만 하고 계속 돌았다 |
| AQE 감지 | 태스크 개수 변화로 추측했다 (AQE는 합치기도 한다) |
| 디스크 제한 | 실험과 다른 I/O 방식으로 검증했다 |
| 실행 감시 | SSH 끊김을 "작업 완료"로 오판했다 |

전부 같은 모양이다. **확인한다고 한 것이 실제로 확인하려던 것이 아니었다.**

### 3. 2~3번 돌려놓고 결론을 냈다

디스크 실험에서 "6배 느려진다"는 결과가 나왔다. 조건 간 차이가 6배인데 반복 편차는 1% 미만이라 자신 있게 적었다.

72번으로 다시 돌리니 **1.04배**가 나왔다. 뒤집힌 이유는, 그 "편차 1%"가 **한쪽 결과들 안에서만** 1%였기 때문이다. 같은 조건에서 23초와 159초, 두 무리가 있었는데 표본이 적어 한쪽만 본 거였다.

## 그래서 뭘 하면 되나

| 증상 | 어디를 볼 것인가 |
|---|---|
| skew가 커지는데 어느 순간 확 느려진다 | **작업 메모리 풀이 찼는지.** 디스크로 흘린 양은 초반엔 파티션 크기를 대변하지 못한다 |
| AQE를 켰는데 느린 태스크가 남는다 | 파티션의 **행 수.** AQE는 용량만 본다 |
| 좁은 행을 대량으로 다룬다 | 메모리 풀을 다 못 쓸 수 있다. 행을 넓히거나 executor 메모리를 올려라 |
| 디스크로 많이 흘려서 디스크를 의심한다 | NVMe면 아마 아니다. **압축을 꺼보는 게 먼저다** |
| core를 줄이면 메모리가 편해질 줄 알았다 | 최대 사용량은 안 변한다. 바뀌는 건 **한계에 닿는 지점**이다 |
| core를 늘렸더니 OOM이 난다 | 메모리 풀 계산으로는 안 보인다. **풀 밖의 버퍼**가 core 수만큼 는다 |
| 코어를 더 붙여서 skew를 덮으려 한다 | 수익률이 떨어진다. skew 8→32에서 6 core 효과의 24%가 날아갔다 |
| 정렬 기준으로 잰 메모리 한계를 조인에 그대로 쓴다 | 조인이 100MB 먼저 넘친다 (712 vs 616MB) |
| 집계라서 안전할 거라 생각한다 | `count`류는 정말 안전하다. `collect_list`류는 **측정을 못 했을 뿐** 안전하다는 근거가 없다 |

## 이 결과를 어디까지 믿어야 하나

1. **한 종류 환경이다.** m6id.4xlarge, 단일 노드, 8GB 데이터. 여러 노드에 걸친 네트워크 shuffle은 없다.
2. **정렬과 조인은 확인했고, 집계는 못 했다.** 발견 6 참고. 집계는 Spark가 메모리 사용량을 보고하지 않아서 같은 방식으로 잴 수 없었다.
3. **1,741ns/행은 이 조건의 값**이다. 가져갈 것은 숫자가 아니라 **"행 수가 용량을 압도한다"는 구조**다.
4. **좁은 행의 536MB 천장은 가설**이다. 내부 할당을 직접 추적하지 않았다.
5. **디스크 실험은 절반만 성공했다.** 50MB/s에서 5.4배는 깨끗하지만, 그 위에서는
   장비 자체가 76~239MB/s로 널뛰어서 측정이 안 된다.
6. **OOM은 2건뿐이다.** core를 늘리면 OOM이 난다는 건 주장이 아니라 관측으로만 적었다.
7. **첫 방출량이 왜 풀의 75.7%인지는 모른다.** 1/N로 줄어드는 건 측정했지만
   그 계수는 설명하지 못했다.
